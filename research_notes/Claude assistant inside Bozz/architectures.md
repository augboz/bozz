# Technical architectures for letting Claude modify and generate UI inside a React + TypeScript Tauri 2 desktop app (widget grid with JSON config, pages, themes, notes)

Research date: 2026-10-15. All Anthropic API facts verified against platform.claude.com docs fetched today unless marked "skill cache" (the bundled claude-api skill, cached 2026-10-06). Items marked UNVERIFIED were not confirmed against a primary source.

Shorthand used below: A = tool use over a declarative action API; B = generative UI (LLM emits a UI spec rendered by the app); C = code generation into a sandboxed iframe.

## Key question 1: Approach A, tool use over a declarative action API (best practices with the Oct 2026 Claude API; batching, preview, dry-run and confirm patterns)

### Takeaway
Approach A is the best-supported path on the current Claude API: user-defined tools with `strict: true` give grammar-guaranteed schema-valid inputs, parallel tool calls arrive in one assistant message, and the SDK tool runner can be driven iteration by iteration so the app can collect a whole turn's `tool_use` blocks, validate them, show a preview, and only then apply (or reject) them. The one big 2026 change is that forced tool use (`tool_choice: any/tool`) returns 400 on Opus 5.5, Sonnet 5.5 and Fable 5.1, so "always emit an action" must be achieved with `auto` plus prompting, strict tools, or structured outputs.

### Cited Findings
- Tool definition fields: `name` (regex `^[a-zA-Z0-9_-]{1,128}$`), `description`, `input_schema` (JSON Schema), optional `input_examples` (schema-validated examples, ~20-50 tokens each for simple ones, 100-200 for nested objects; invalid examples return 400); optional per-tool properties include `cache_control`, `strict`, `defer_loading`, `allowed_callers` — [Define tools](https://platform.claude.com/docs/en/agents-and-tools/tool-use/define-tools)
- Anthropic's stated best practices: "extremely detailed descriptions" (3-4+ sentences), consolidate related operations into fewer tools with an `action` parameter rather than one tool per verb (their example: `create_pr`/`review_pr`/`merge_pr` -> one tool), namespace tool names by service, return only high-signal stable identifiers (slugs/UUIDs) in tool results, and ask for a short "explanation" rather than "reasoning" in parameters because a reasoning parameter can trigger a `reasoning_extraction` refusal — [Define tools](https://platform.claude.com/docs/en/agents-and-tools/tool-use/define-tools)
- Forced tool use: `tool_choice: {"type":"any"}` and `{"type":"tool","name":...}` return a 400 on Claude Opus 5.5, Claude Sonnet 5.5, Claude Fable 5.1 and Claude Mythos 5.1; `auto` and `none` still work. Recommended replacements: `auto` + strict tool use to guarantee schema-valid inputs, or structured outputs when you need a fixed JSON shape; "prompting still influences which tool `auto` picks". Also, on models that still accept forcing, a forced call skips thinking entirely — [Define tools](https://platform.claude.com/docs/en/agents-and-tools/tool-use/define-tools)
- Changing `tool_choice` invalidates cached message blocks (tool definitions and system prompt stay cached) — [Define tools](https://platform.claude.com/docs/en/agents-and-tools/tool-use/define-tools); confirmed in [Prompt caching](https://platform.claude.com/docs/en/build-with-claude/prompt-caching) ("`tool_choice` changes: invalidate only messages")
- Strict tool use: set `strict: true` on the tool definition; it "guarantees that tool names and inputs match the tool's schema, using grammar-constrained sampling"; strict tools and JSON structured outputs can be combined in one request. Limits: max 20 strict tools per request (non-strict don't count), max 24 optional parameters across all strict schemas, max 16 parameters using `anyOf`/type arrays; "Schema is too complex for compilation" 400 beyond internal grammar limits; 180 s compile timeout; first request with a new schema has extra latency; compiled grammars cached 24 h from last use and invalidated by schema structure changes or changes to the set of tools (not by `name`/`description` changes) — [Structured outputs](https://platform.claude.com/docs/en/build-with-claude/structured-outputs)
- JSON Schema subset for strict/structured outputs: object/array/string/integer/number/boolean/null; `enum` (primitives only), `const`, `anyOf`, `allOf` (not with `$ref`), internal `$ref`/`$defs`, `default`, `required`, `additionalProperties` must be `false`; string formats date-time/time/date/duration/email/hostname/uri/ipv4/ipv6/uuid; `minItems` only 0 or 1. NOT supported: recursive schemas, external `$ref`, numeric constraints (`minimum`/`maximum`/`multipleOf`), string length constraints, other array constraints. Unsupported features return 400; SDK helpers may move them into descriptions and validate locally. Output property order is required-first then optional, in schema order; enum values may differ only in capitalization so compare case-insensitively — [Structured outputs](https://platform.claude.com/docs/en/build-with-claude/structured-outputs)
- Structured outputs API shape: `output_config: {format: {type: "json_schema", schema: {...}}}`; the older `output_format` parameter is deprecated and beta headers are no longer required; Python `client.messages.parse()` and TypeScript `zodOutputFormat()` build and parse; structured outputs inject a system prompt (counts as input tokens) and changing `output_config.format` invalidates the prompt cache for that thread; refusals return 200 with `stop_reason: "refusal"` and output may not match the schema; `stop_reason: "max_tokens"` means incomplete JSON — [Structured outputs](https://platform.claude.com/docs/en/build-with-claude/structured-outputs)
- Parallel tool use is on by default: one assistant message may contain multiple `tool_use` blocks; execute them and return ALL `tool_result` blocks in a single user message (splitting them across messages "silently trains Claude to stop making parallel calls"); failed tools should be returned with `is_error: true`, not dropped; `disable_parallel_tool_use` still works with `auto` — skill cache (claude-api skill, Tool Use Patterns), consistent with [Define tools](https://platform.claude.com/docs/en/agents-and-tools/tool-use/define-tools)
- Tool Runner (SDK beta): TypeScript `betaZodTool()` from `@anthropic-ai/sdk/helpers/beta/zod` (needs Zod >= 3.25.0) or `betaTool()` for JSON Schema, run with `client.beta.messages.toolRunner({...})`; the runner "loops until Claude returns a message without a tool use, or until it reaches `max_iterations`"; you can iterate the runner, read each response message and "modify the runner's state before the next API call"; if you take over an iteration you must append the assistant message and tool results yourself. Anthropic's own doc says: "When you need human-in-the-loop approval, custom logging, or conditional execution, use the manual loop instead" — [Tool runner (SDK)](https://platform.claude.com/docs/en/agents-and-tools/tool-use/tool-runner)
- Tool Runner compaction: TypeScript/Ruby client-side compaction is deprecated in favour of server-side compaction via `context_management`; `compactBeforeNextTurn()` helper exists for on-demand compaction — [Tool runner (SDK)](https://platform.claude.com/docs/en/agents-and-tools/tool-use/tool-runner)
- Eager input streaming (fine-grained tool streaming) is not a beta: set `eager_input_streaming: true` on the tool definition and use `client.messages.stream(...)`; with it on, the API no longer coerces/validates the input, so accumulated `partial_json` may be incomplete (`max_tokens`) or invalid and the client must validate against the schema before executing; the legacy `fine-grained-tool-streaming-2025-05-14` beta header should not also be sent — skill cache (claude-api skill, Common Pitfalls and Defaults)
- Prompt caching facts relevant to a stable tool set: prefix order is `tools` -> `system` -> `messages`; any change at a level invalidates that level and all later ones; changing tool definitions (names, descriptions, parameters) invalidates tools+system+messages; up to 4 explicit `cache_control` breakpoints; top-level `cache_control: {type:"ephemeral"}` auto-caches up to the last cacheable block and moves the breakpoint forward as the conversation grows; minimum cacheable prefix 512 tokens on Opus 5.5 / Sonnet 5.5 / Haiku 5.5 / Fable 5.1; 5-minute TTL refreshed free on read, 1 h TTL via `ttl: "1h"`; writes 1.25x (5m) / 2x (1h); reads 0.1x by default but 0.05x on Opus 5.5 and Sonnet 5.5 and 0.025x on Fable 5.1; thinking config or `output_config.effort` changes invalidate messages (on some models also tools and system) — [Prompt caching](https://platform.claude.com/docs/en/build-with-claude/prompt-caching)
- Mid-conversation operator instructions: append `{role: "system", content: ...}` to `messages[]` instead of editing top-level `system`, on Opus 5.5 / Opus 5 / Fable 5.1 / Sonnet 5.5 / Haiku 5.5 (not Sonnet 5), no beta header; must follow a user message and be last or followed by an assistant turn; preserves the cached prefix and is described as "the prompt-injection-safe operator channel" — skill cache (claude-api skill, Mid-Conversation System Messages)
- Model/API consequences of Fable 5.1 / Opus 5.5 / Sonnet 5.5 for tool loops: no assistant prefill (400), thinking cannot be disabled on Opus 5.5 (effort is the only lever, default `medium`), thinking blocks are bound to the producing model and to an append-only conversation ("preserved thinking": editing earlier turns invalidates thinking blocks, enforced with 400 for accounts created on/after 2026-08-31), so an action-undo loop must be append-only in the transcript and must not rewrite earlier tool calls — skill cache (claude-api skill, Claude Fable 5.1 / Opus 5.5 / Sonnet 5.5 sections)
- Anthropic's eval guidance for state-modifying agents: grade the final environment state (e.g. the record exists), not the agent's claim of success; do not grade a rigid step sequence because agents find valid alternative paths; transcripts are still useful for constraints like required tool calls and turn limits; start with 20-50 tasks drawn from real failures; run multiple trials from a clean environment; `pass^k` for customer-facing consistency (75% per trial gives roughly 42% pass^3); run evals on every agent change and model upgrade — [Demystifying evals for AI agents, Anthropic, 2026-01-09](https://anthropic.com/engineering/demystifying-evals-for-ai-agents)
- Managed Agents (Anthropic's hosted agent surface) exposes tool permission policies `always_allow` / `always_ask` / `auto` with a `tool_confirmation` round trip that pauses the session until the client approves — skill cache (claude-api skill, Managed Agents, Permission Policies). This is the server-side analogue of a confirm-before-apply gate.
- Trajectory evals as deterministic checks: LangChain `agentevals` offers strict / unordered / subset / superset trajectory match modes (strict = exact tool calls in order, useful for "check policy before authorizing"; subset catches an agent reaching beyond scope) — [LangChain evals docs](https://docs.langchain.com/oss/javascript/langchain/evals)

### Inferences
- The cleanest "batch + preview" design under the Oct 2026 API: run the manual loop (or iterate the tool runner), collect every `tool_use` block in the assistant message (parallel calls arrive together), validate each against the app's own Zod schema (even with `strict: true`, because `eager_input_streaming` and `max_tokens` cutoffs can produce truncated inputs), simulate the batch against a cloned store to produce a diff/preview, and only after the user confirms (or an auto-apply policy passes) commit and return `tool_result` blocks. Rejected actions should be returned as `tool_result` with `is_error: true` and a human-readable reason ("user declined"), which keeps the transcript append-only and compatible with preserved thinking.
- Because forced tool use is gone, a "plan then apply" shape is better expressed as: tool_choice `auto`, a system instruction such as "Use the `apply_changes` tool for any change to the dashboard; never describe changes without calling it", and `strict: true` on the action tool. If you only need one JSON plan per turn (no multi-step), structured outputs (`output_config.format`) with a schema `{actions: [...]}` is simpler than tools and avoids the tool-loop entirely; but it cannot interleave reads (e.g. `list_pages`) before deciding.
- Anthropic's consolidation advice points towards a small tool surface for Bozz: e.g. `read_dashboard` (returns pages/widgets/theme as compact JSON with stable ids), `apply_changes` (array of typed ops with a discriminated `op` field) and maybe `create_custom_widget` (Approach C). One op-array tool keeps you under the 20-strict-tool / 24-optional-parameter limits and gives you a natural batch boundary for preview + undo.
- Strict-schema limits matter for an "ops union": a discriminated union of ~10 op types with several optional fields each will hit the 24-optional-parameter cap quickly. Mitigations are the ones Anthropic lists: make parameters required (use `null` via `.nullable()` rather than optional), flatten, or mark only the ops tool strict.
- Undo should be implemented at the app level as an inverse-op journal keyed by `tool_use.id`, not by rewriting the conversation. Keep the transcript append-only and tell Claude about the undo in a new user/system message if needed.

### Gaps
- No official Anthropic doc describes a "dry-run/confirm" pattern for the Messages API specifically; the only first-party confirm mechanism found is Managed Agents' `tool_confirmation`. The manual-loop recommendation for human-in-the-loop is explicit but pattern details are inferred.
- I did not find published case studies of apps batching multiple tool calls into one preview with undo; the pattern is inferred from the API's parallel-tool and tool-result semantics plus the trajectory-eval literature.
- I did not read the "Handle tool calls" page in full; details on `pause_turn` handling and `max_tokens` mid-tool-call recovery are from the skill cache, not re-verified today.

## Key question 2: Approach B, generative UI (LLM emits a UI spec the app renders): Vercel AI SDK, json-render, A2UI, Thesys C1 / OpenUI, CopilotKit / AG-UI, OpenAI Apps SDK, MCP Apps

### Takeaway
Every production-grade generative-UI system converged on the same rule: the model emits a declarative spec constrained to a developer-approved component catalog, validated at runtime, and rendered by app-owned components; executable code is never emitted (MCP Apps / OpenAI Apps SDK are the exception, and they treat the HTML as a predeclared server resource in a sandboxed iframe, not something the model writes). For a widget grid with JSON config, json-render (Vercel Labs) and A2UI (Google) are the closest fits; CopilotKit/AG-UI and the AI SDK are "tool call -> React component" bindings rather than spec languages.

### Cited Findings

- Core API: `defineCatalog(schema, { components, actions })` with Zod `props` and `description` per component; `defineRegistry(catalog, { components })` maps to real React components; `<Renderer spec={spec} registry={registry} />`; `catalog.prompt()` generates the system prompt; flat spec format = `root` + `elements` map where each element has `type`, `props`, `children` — [GitHub json-render](https://github.com/vercel-labs/json-render)

**Failure modes and defenses (generative UI)**
- Four failure layers for GenUI: structural (output matches no component), semantic (valid component but the wrong one), data (right component, fabricated values), safety (complies with a request it should refuse); "no single defense catches all four" — [Very Good Ventures, four-layer defense](https://verygood.ventures/blog/generative-ui-hallucinations-four-layer-defense.md)
- Their concrete Layer 1: catalog JSON Schemas injected into the system prompt plus two validators (envelope shape, catalog membership); on failure, return the errors to the model with "reissue using only components from the catalog" and retry once, then error out rather than ship broken output. Layer 3: ground data via tools and a `PromptContextBuilder` that injects server-known facts (never secrets or unscreened client input). Layer 4: a screening layer (they use Google Model Armor) on prompt and response — [Very Good Ventures](https://verygood.ventures/blog/generative-ui-hallucinations-four-layer-defense.md)
- "The obvious failures are the manageable ones: the model emits invalid JSON, the schema validator rejects, the fallback renders. The more dangerous ones are the quiet failures that pass validation"; the validator must run on every output at runtime (e.g. a List whose children are not list items, a Select with no options) and the fallback path is "a first-class product surface" — [tianpan.co, Generative UI as a production discipline, 2026-04-27](https://tianpan.co/blog/2026-04-27-generative-ui-production-discipline)
- "Generative UI that constrains the model to select and configure a fixed inventory of components is dramatically more reliable than generative UI that lets the model invent the interface" — [metacto production guide](https://www.metacto.com/blogs/generative-ui-production-guide)
- In a benchmark of LLM-generated executable web apps, the largest single failure cause was a hallucinated icon import (34.7% of failures) — [UI2App, arXiv 2607.06306](https://arxiv.org/pdf/2607.06306)

### Inferences
- For Bozz, "generative UI" in the pure sense (the model lays out arbitrary UI) is mostly unnecessary: the app already has a catalog (widget types with JSON config). The B-style win is to expose the widget catalog as the "component vocabulary" and let the model emit widget configs, which collapses into Approach A (an `add_widget` op whose `config` is the per-widget Zod schema). json-render's catalog/registry split is a good mental model even if you do not adopt the library.
- json-render is the most React-native and most actively developed option, but its README documents no runtime security story beyond "only catalog components", and its state/expression layer (`$state`, `$computed`, `watch`) is a mini language the model can misuse; if adopted, validate the final spec with the catalog's Zod schemas on every chunk and keep expressions out of the catalog unless needed.
- A2UI's React story is weak today (Angular/Flutter/Lit renderers; React only as a "target"); it is better suited to cross-agent interop than an in-app widget grid. CopilotKit is a full framework (chat UI + agent runtime) and would be heavy for a Tauri app that already has its own UI and calls Claude directly.
- OpenUI/Thesys's token-compact DSL plus "Autofix" is an interesting cost lever, but it is a hosted gateway with a company-specific language; adopting it couples the app to a vendor. Documentation reorganisation (docs.thesys.dev -> openui.com) suggests the product is in flux.
- Streaming partial render is uniformly done via a line- or patch-oriented stream (json-render patches, OpenUI per-line, A2UI message stream, AI SDK tool-part states); with the Claude API the matching primitive is `eager_input_streaming` on a strict tool, which streams the ops array as it is produced so the app can show a growing preview.

### Gaps
- json-render's semantic version number, the patch/merge/diff edit modes, and any security audit are not on the README; the version-specific claims come from secondary articles.
- A2UI's exact message type list (`surfaceUpdate`, `dataModelUpdate`, `beginRendering`) and React renderer status were not confirmed on a2ui.org's landing page; the spec pages were not fetched.
- Thesys C1 pricing, current SDK package names/versions (`@thesys/genui-sdk`, crayon) and whether C1 and OpenUI are now the same product were not verifiable; docs.thesys.dev redirects to openui.com but openui.com does not mention C1.

## Key question 3: Approach C, code generation into a sandboxed iframe inside a Tauri 2 app (security requirements, persistence, editing, data access)

### Takeaway
Running model-written HTML/JS is feasible inside Tauri 2 if, and only if, the iframe is sandboxed with `allow-scripts` and WITHOUT `allow-same-origin`, carries its own restrictive CSP, and talks to the host only via a narrow validated `postMessage` protocol; Tauri's own IPC is not injected into sub-frames since the CVE-2024-35222 fix, but on Windows a same-origin iframe can still reach `invoke`, which is exactly why `allow-same-origin` must never be granted. MCP Apps is the most complete published spec of this pattern (sandbox proxy, CSP from declared domains, JSON-RPC over postMessage) and can be copied for an in-app "custom widget" host.

### Cited Findings
**Browser sandbox primitives**
- `sandbox` tokens include `allow-forms`, `allow-modals`, `allow-popups`, `allow-popups-to-escape-sandbox`, `allow-same-origin`, `allow-scripts`, `allow-top-navigation`, `allow-top-navigation-by-user-activation`, `allow-downloads`, `allow-storage-access-by-user-activation`; without `allow-same-origin` the content "is treated as a special origin that always fails the same-origin policy"; MDN: "it is strongly discouraged to use both `allow-scripts` and `allow-same-origin`, as that lets the embedded document remove the `sandbox` attribute, making it no more secure than not using the sandbox attribute at all" — [MDN iframe](https://developer.mozilla.org/en-US/docs/Web/HTML/Reference/Elements/iframe)
- `srcdoc` overrides `src`; the document's location is `about:srcdoc`; relative URLs resolve against the embedding page (so a sandboxed `srcdoc` frame with a tauri:// parent would resolve relative URLs against the app origin, another reason to pin a CSP); content must be HTML-escaped and `&`/`"` escaped when placed in the attribute; `credentialless` iframes get an ephemeral context with no cookies/storage; the `allow` attribute sets Permissions Policy (camera, microphone, etc.) and only adds restrictions on top of the header — [MDN iframe](https://developer.mozilla.org/en-US/docs/Web/HTML/Reference/Elements/iframe)
- `<meta http-equiv="Content-Security-Policy">` injected at the top of iframe content is obeyed even if later untrusted JS tries to manipulate it (Simon Willison's finding while building an artifact-style tool, not an Anthropic mechanism) — [Simon Willison via search](https://simonwillison.net/2024/Aug/28/how-anthropic-built-artifacts)

**Tauri 2 specifics**
- CVE-2024-35222 / GHSA-57fm-592m-34r7 (CVSS 5.9): remote-origin iframes could reach Tauri IPC without being allowed in `dangerousRemoteDomainIpcAccess` (v1) or `capabilities` (v2); fixed in 1.6.7 and 2.0.0-beta.19/20. Fix: "The Tauri invoke functionality is no longer accessible from iFrames, except on Windows when the origin of the Tauri window and the origin of the iFrame are the same"; a `__TAURI_INVOKE_KEY__` blocks frames not initialised by Tauri core from posting to IPC, and this key "is only intended to block IPC access from sub-frames", not to protect against a compromised main window; workaround advice: "use a dedicated window for untrusted origins instead of iFrames, or disable script execution within the iFrame"; on Linux v2 "multiple WebViews in the main window" can simulate iframes — [GHSA-57fm-592m-34r7](https://github.com/advisories/GHSA-57fm-592m-34r7)
- Tauri CSP is configured in `app.security.csp` (string or directive object) and "is only enforced if set"; Tauri hashes local scripts and nonces styles/external scripts at compile time; the docs advise allowing only hosts you own and against loading remote scripts (CDNs); `'wasm-unsafe-eval'` needed for WebAssembly — [Tauri CSP](https://v2.tauri.app/security/csp/)
- Config reference: `app.security.dangerousDisableAssetCspModification` (default false; `true` disables all CSP modification, or a list of directives), `app.security.pattern` default `"brownfield"` with `"isolation"` "Recommended for security purposes", `app.security.assetProtocol` disabled by default with allow/deny scope, `app.withGlobalTauri` default false (injects the API onto `window.__TAURI__` when true), `Capability.remote.urls` (URLPattern list of remote domains that can use a capability; docs warn to "understand the security implications of providing remote sources with local system access"), `app.security.headers` for COOP/COEP — [Tauri config reference](https://v2.tauri.app/reference/config/)
- Isolation pattern: Tauri injects an "Isolation application" that runs in a sandboxed `<iframe>`; every IPC call is routed through its `window.__TAURI_ISOLATION_HOOK__`, which can validate or modify the payload, then the message is AES-GCM encrypted via SubtleCrypto with a fresh key per app run before the main frontend hands it to Core; configure with `app.security.pattern.use = "isolation"` and `options.dir`; limitation: "External script files don't load reliably in sandboxed iframes on Windows", so Tauri inlines scripts at build time, and ES modules do not work in that frame; encryption overhead is small — [Tauri isolation pattern](https://v2.tauri.app/concept/inter-process-communication/isolation/)

**MCP Apps host requirements (reusable blueprint)**
- Web hosts "must wrap the View in a sandbox proxy with a different origin"; the proxy iframe needs `allow-scripts` and `allow-same-origin` (because it is on a separate origin); "Desktop and native hosts can render the View in an iframe directly"; handshake: proxy sends `ui/notifications/sandbox-proxy-ready`, host replies `ui/notifications/sandbox-resource-ready` with the HTML, CSP settings and permissions; host must not send anything to the View until `ui/notifications/initialized` — [ext-apps spec](https://raw.githubusercontent.com/modelcontextprotocol/ext-apps/main/specification/draft/apps.mdx)
- CSP construction from `_meta.ui.csp`: `connectDomains` -> `connect-src`; `resourceDomains` -> `img-src`, `script-src`, `style-src`, `font-src`, `media-src`; `frameDomains` -> `frame-src` (default `'none'`); `baseUriDomains` -> `base-uri` (default `'self'`); `object-src 'none'` always; default when omitted: deny everything, scripts/styles self + inline, images/media self + `data:`, network blocked; "Hosts may restrict further but must not allow undeclared domains" — [ext-apps spec](https://raw.githubusercontent.com/modelcontextprotocol/ext-apps/main/specification/draft/apps.mdx)
- JSON-RPC over postMessage methods: View -> Host `ui/initialize`, `ui/notifications/initialized`, `tools/call`, `tools/list`, `resources/read`, `ui/message`, `ui/open-link`, `ui/download-file`, `ui/update-model-context`, `ui/request-display-mode` (`inline`/`fullscreen`/`pip`), `ui/notifications/size-changed`, `ui/notifications/request-teardown`, `notifications/message`, `sampling/createMessage`, `ping`; Host -> View `ui/notifications/tool-input`, `tool-input-partial` (streaming), `tool-result`, `tool-cancelled`, `host-context-changed` (theme `light`/`dark`, CSS variables in `styles.variables`, fonts in `styles.css.fonts`, display mode, dimensions), `ui/resource-teardown` — [ext-apps spec](https://raw.githubusercontent.com/modelcontextprotocol/ext-apps/main/specification/draft/apps.mdx)
- Threat model: malicious HTML, sandbox escape, unauthorized tool execution, exfiltration of host data, phishing, resource exhaustion. Mitigations: sandboxed iframes with all communication via postMessage; validate and log every JSON-RPC message; pre-connection review via hashing/allowlists; CSP that blocks undeclared domains; user confirmation for side-effecting tool calls (scaled by `readOnlyHint`); tool-name namespacing; recommended limits 50 tools per app, 30 s callback timeouts, 10 MB results; app tool registrations must not persist across sessions; also "social engineering through misleading UI content" and CPU/memory exhaustion — [ext-apps spec](https://raw.githubusercontent.com/modelcontextprotocol/ext-apps/main/specification/draft/apps.mdx)
- Extension id `io.modelcontextprotocol/ui`; MIME `text/html;profile=mcp-app`; SDK `@modelcontextprotocol/ext-apps` (`App` class, `registerTool()`, `PostMessageTransport`) and `@modelcontextprotocol/ext-apps/server` (`getUiCapability`, `RESOURCE_MIME_TYPE`); the flat `_meta["ui/resourceUri"]` key is deprecated in favour of `_meta.ui.resourceUri`; `_meta.ui.visibility` can hide tools from the model (`"app"` only) — [ext-apps spec](https://raw.githubusercontent.com/modelcontextprotocol/ext-apps/main/specification/draft/apps.mdx)
- SEP-1865 status: "Final", Extensions Track, created 2025-11-21; design informed by MCP-UI (community reference implementation, mcpui.dev) and OpenAI's Apps SDK; "Global API object" was rejected in favour of JSON-RPC because it "requires host-specific injection and doesn't work with external iframe sources"; HTML-only MVP chosen for "simplest security model (standard iframe sandbox)" and screenshot ability — [SEP-1865](https://modelcontextprotocol.io/seps/1865-mcp-apps-interactive-user-interfaces-for-mcp)
- A secondary source states the spec was ratified as dated specification 2026-01-26 and ships as official in the 2026-07-28 MCP release, with host support in Claude, ChatGPT, VS Code and Goose (UNVERIFIED on modelcontextprotocol.io) — [mcp.directory](https://mcp.directory/blog/mcp-apps-spec-2026-when-should-your-server-render-ui)

**Prior art for sandboxing model-written UI**
- Anthropic on Artifacts (2024): "iframe sandboxes with process isolation" plus "strict Content Security Policies (CSPs) to enforce limited and controlled network access"; the biggest challenge was "building a robust sandbox to run the LLM-generated code in" — [Simon Willison, How Anthropic built Artifacts](https://simonwillison.net/2024/Aug/28/how-anthropic-built-artifacts)
- Artifacts behaviour reported by developers: sandboxed iframe blocks `localStorage`/`sessionStorage`; `connect-src 'self'` so page code reaches only its own sandbox origin; camera/microphone/geolocation denied; a later `window.claude.complete()` bridge lets artifact JS run prompts billed to the signed-in user (Willison flagged this as a deliberate hole) — [search summary of Willison / Pluto Security](https://pluto.security/blog/inside-claude-artifacts-how-your-agent-publishes-to-the-web/)
- Claude Cowork local artifacts "are written to disk and rendered inside Claude Desktop under a custom scheme, in an isolated app partition, so nothing leaves the machine" (secondary) — [Pluto Security](https://pluto.security/blog/inside-claude-artifacts-how-your-agent-publishes-to-the-web/)
- `safe-content-frame` (assistant-ui, npm `safe-content-frame`, no dependencies, built on Google's SafeContentFrame design): "Every render gets its own iframe and origin" at `https://<hash>.scf.auiusercontent.com` (suffix on the Public Suffix List so renders do not share storage); the frame accepts content only from your page's origin via `?origin=`; `sendMessage()` targets the exact origin (a plain sandboxed iframe can only `postMessage` with `"*"`); API: `renderHtml()`, `renderPdf()`, `renderRaw()`, `dispose()`, `useShadowDom`, `enableBrowserCaching`; stated use cases: MCP Apps and LLM-generated HTML — [assistant-ui safe-content-frame](https://www.assistant-ui.com/safe-content-frame)
- Sandpack: the bundler/client iframe is loaded from a third-party domain (codesandbox.io) by default; the maintainer's advice for isolation is to self-host the same static files on a separate origin at the cost of losing automatic bundler updates — [Sandpack discussion #1061](https://github.com/codesandbox/sandpack/discussions/1061)
- WebContainers "leverage the web browser's built-in sandboxing capabilities" but "greater responsibility comes with WebContainer APIs"; they need COOP/COEP (cross-origin isolation) headers — [StackBlitz interview](https://blog.stackblitz.com/posts/beyond-docker-webcontainers-and-the-future-of-web-dev-interview-with-joan-varvenne/)

### Inferences
- Minimal secure recipe for a Bozz "custom widget" host (derived from MDN + Tauri advisory + MCP Apps):
  1. `<iframe sandbox="allow-scripts" srcdoc={html}>` with no `allow-same-origin`, no `allow-forms`/`allow-popups`/`allow-top-navigation` unless a feature needs it; set `allow=""` (no camera/mic/geo); set `referrerpolicy="no-referrer"`.
  2. Prepend a `<meta http-equiv="Content-Security-Policy">` to the srcdoc: `default-src 'none'; script-src 'unsafe-inline'; style-src 'unsafe-inline'; img-src data:; connect-src 'none'; frame-src 'none'; object-src 'none'; base-uri 'none'`. This mirrors MCP Apps' default policy and Artifacts' network lockdown. Allow specific `connect-src` domains only if the user opts in per widget (the MCP Apps `connectDomains` idea).
  3. Because the frame has an opaque origin, `postMessage` from the parent must use `"*"` targetOrigin; the parent must therefore check `event.source === iframe.contentWindow` and ignore `event.origin` (which will be `"null"`), and must validate every message against a Zod schema; messages should be JSON-RPC-style with a small whitelist: `widget/ready`, `widget/size-changed`, `widget/request-data`, `widget/action` (optional, gated by user confirmation), and host -> widget `host/data` (read-only JSON snapshot of tasks/notes), `host/theme`.
  4. Never inject `window.__TAURI__` (keep `withGlobalTauri: false`) and never grant `allow-same-origin`; the Windows carve-out in the CVE fix means a same-origin frame can reach `invoke`. Keep the main app CSP in `tauri.conf.json` with `frame-src 'self'` (srcdoc frames are allowed by `'self'`/`about:` in practice; verify on WebView2 and WKWebView).
  5. Consider the Tauri isolation pattern for the app overall; it does not replace the per-widget sandbox but it adds an IPC validation hook in case a widget ever escapes to the main frame.
- Persistence: store the generated source as a widget config field (e.g. `{type: "custom", source: {html: string, version: n, generatedBy: "claude", promptHash}}`) in the same user data store as other widgets, so sync/backup/undo behave uniformly; keep a per-widget version history so "edit this widget" can be an LLM call that receives the current source and returns a full replacement (Claude 5.x models' tool inputs can be large; stream with `eager_input_streaming`). Diff-based edits (text_editor style `str_replace`) are an option but whole-file replacement is simpler to validate and preview.
- Data access: push a read-only, pre-filtered JSON snapshot via `postMessage` (not a live store reference), re-sent on change; never pass tokens, emails or sync credentials. If the widget needs to mutate data, route it through the same `apply_changes` op pipeline as Approach A with the same confirm gate, so there is exactly one write path.
- Known failure modes to expect: generated widgets that import from CDNs (blocked by CSP; tell the model "no external resources, inline everything, no imports"), use `localStorage` (unavailable in an opaque-origin sandbox; Artifacts had the same complaint), rely on `fetch`, or exceed CPU (add a watchdog: tear down a frame that does not answer `ping`). The UI2App benchmark's "hallucinated icon import" failure is the same class.
- Windows caveat from the Tauri isolation docs ("external script files don't load reliably in sandboxed iframes on Windows") supports inlining everything into the srcdoc rather than referencing files.

### Gaps
- I did not find a Tauri 2 doc that states how `srcdoc` iframes interact with the `tauri://localhost` (Windows: `http://tauri.localhost`) origin or whether `frame-src 'self'` is required for them; test on WebView2 and WKWebView.
- No published case study of a Tauri app hosting LLM-generated widgets was found; Obsidian Datacore/Dataview and Scriptable were not researched (they execute trusted user scripts with full plugin privileges, which is a different threat model from model-generated code; UNVERIFIED).
- Exact sandbox attributes used by Claude Artifacts, `safe-content-frame`, and MCP Apps' inner View iframe are not published on the pages fetched.
- The "Claude Code web" and v0/Bolt sandboxing internals were not researched (Bolt is built on WebContainers; v0 internals are not public).

## Key question 4: Hybrid (declarative actions for app changes + sandboxed code only for "custom widget" requests) and case studies

### Takeaway
The hybrid is what the two largest "apps inside chat" platforms actually ship: both OpenAI's Apps SDK and MCP Apps combine structured tool calls (for state) with a sandboxed HTML View (for presentation), and every View-initiated side effect is routed back through a tool call that the host can gate. No public case study of this hybrid inside a desktop productivity app was found; the pattern is inferred from those specs.

### Cited Findings
- MCP Apps separates "data tools" (return results, no template) from "render tools" (carry `_meta.ui.resourceUri`); the View can only change app state by calling `tools/call`, which the host proxies and may require approval for depending on `readOnlyHint` — [ext-apps spec](https://raw.githubusercontent.com/modelcontextprotocol/ext-apps/main/specification/draft/apps.mdx), [OpenAI Apps SDK](https://developers.openai.com/apps-sdk/build/custom-ux)
- OpenAI: "Business data stays on the server. Widget state is not a source of truth or durable storage"; widget `setWidgetState` is scoped to one widget instance — [OpenAI Apps SDK](https://developers.openai.com/apps-sdk/build/custom-ux)
- Google's framing of the two camps: MCP "treats UI as a resource, typically prefab HTML loaded in a sandbox" vs A2UI's native-first declarative catalogs — [The Decoder](https://the-decoder.com/googles-open-standard-lets-ai-agents-build-user-interfaces-on-the-fly/)
- Claude Artifacts added `window.claude.complete()` so artifact code can call Claude, billed to the signed-in user; Willison called it a deliberate hole — [search summary (Willison)](https://simonwillison.net/2024/Aug/28/how-anthropic-built-artifacts)
- The Claude desktop runtime this research was produced in exposes Artifacts "capabilities" (db, assets, shared state, "ask Claude a question") to published pages, i.e. the same hybrid (sandboxed page + host-mediated capabilities) is used by Anthropic's own products — observed from the Artifact tool description in this session (first-party tool text, not a public doc; UNVERIFIED externally)

### Inferences
- Recommended decomposition for Bozz: (1) `read_dashboard` / `apply_changes` strict tools cover 90% of requests (add/move/resize/configure widget, create page, set theme, edit note) with a single preview-and-confirm pipeline and inverse-op undo; (2) `create_custom_widget` / `update_custom_widget` ops carry sandboxed HTML as a widget config and go through the same confirm gate; (3) the sandbox bridge exposes read-only data and a single `widget/action` message that is translated into `apply_changes` ops, so the widget cannot bypass the gate.
- Treat the model's generated HTML like MCP Apps treats a server's HTML: hash it, store it with provenance, show the user a review step on first install and on every regeneration, and allow a per-widget network allowlist (default none).

### Gaps
- No published post-mortem or case study from a shipping desktop app using this hybrid was found; HN/Reddit discussions were not located within the tool-call budget.

### Inferences
- In a Tauri app the WebView is effectively a browser: calling `api.anthropic.com` from the React side requires the dangerous header (`dangerouslyAllowBrowser: true` in the TS SDK) and a key in JS memory. Two safer options: (a) do the Messages call from the Rust side (`reqwest`) with the key stored via the OS keychain (e.g. `tauri-plugin-stronghold` or keyring crate), streaming SSE back to the WebView via Tauri events; (b) a tiny proxy on your own domain that exchanges the user's app session for a scoped Anthropic call (also lets you meter per user). "Bring your own key" is the only case where the direct-browser header is defensible, and even then the key should be stored by the Rust side, not in `localStorage`.
- Note the Tauri CSP consequence: whichever path you pick, `connect-src` must include `https://api.anthropic.com` (direct) or your proxy host, and nothing else.
- Cost envelope for a dashboard assistant turn (rough, from the pricing table): a 6K-token cached system+tools prefix plus 2K fresh tokens and 1K output on Sonnet 5.5 is about $0.0006 cached prefix + $0.004 fresh + $0.01 output, roughly $0.015 per turn; on Haiku 5.5 about 20x cheaper; on Opus 5.5 roughly 2x Sonnet. Haiku 5.5 is plausible for `apply_changes` planning if evals show acceptable accuracy; Opus/Sonnet for custom-widget code generation.

## Key question 6: Evaluation/testing of LLM-driven UI changes and guardrails (schema validation, allowlists, max changes per turn)

### Takeaway
The consensus from Anthropic's eval guidance and the GenUI practitioner literature is: validate every model output at runtime (schema + catalog + semantic invariants), grade evals on the resulting app state rather than on the exact tool sequence, keep a deterministic regression suite that runs on every prompt/model change, and reserve LLM-as-judge for subjective layout quality.

### Cited Findings
- Anthropic: code graders for "state or tool-call checks", model graders for nuance with an "Unknown" option and calibration against humans; "verify the final state directly (database records, files, configs), not the agent's confirmation message"; "make graders resistant to shortcuts"; keep regression suites near 100% and promote saturated capability evals into them; start from 20-50 real failures; multiple trials from a clean environment; watch for eval saturation — [Demystifying evals for AI agents](https://anthropic.com/engineering/demystifying-evals-for-ai-agents)
- LangChain `agentevals` trajectory matching: strict / unordered / subset / superset modes; "trajectory match suits cases where you know the expected tool calls, while LLM-as-judge suits assessing overall quality" — [LangChain evals docs](https://docs.langchain.com/oss/javascript/langchain/evals)
- "Deterministic (code-based) checks should handle 60-70% of your eval surface, with LLM-as-judge reserved for subjective qualities"; golden datasets versioned with prompts in Git and run in CI — [Evaluate AI agents in production, 2026](https://www.kunalganglani.com/blog/evaluate-ai-agents-production-testing.md)
- Many agent behaviours "only emerge when using a real LLM, such as which tool the agent decides to call", so mocked tests miss them — [LangChain test docs](https://docs.langchain.com/oss/python/langchain/test)
- GenUI evals: hold out a scenario set, score each failure axis with a calibrated model judge, track scores over time with regression alerts, and compare rendered UIs across prompt versions ("design review is a comparison of two distributions over UI outputs given a scenario set") — [tianpan.co](https://tianpan.co/blog/2026-04-27-generative-ui-production-discipline)
- Runtime validation + retry-once pattern: return validator errors to the model with "reissue using only components from the catalog", retry once, then fail loudly — [Very Good Ventures](https://verygood.ventures/blog/generative-ui-hallucinations-four-layer-defense.md)
- MCP Apps recommended resource limits as a guardrail template: 50 tools per app, 30 s callback timeouts, 10 MB results, confirmation for side-effecting tools — [ext-apps spec](https://raw.githubusercontent.com/modelcontextprotocol/ext-apps/main/specification/draft/apps.mdx)
- Guardrails that run "before each tool execution step, including argument validation" are the standard shape studied in agent-failure benchmarks — [GuardianAgentBench, arXiv 2607.20982](https://arxiv.org/pdf/2607.20982)

### Inferences
- Concrete test plan for Approach A in Bozz: (1) unit-test the op applier as a pure function `(store, ops) -> store` with snapshot tests of the resulting store (this is the "final state" Anthropic recommends and is fully deterministic, no LLM); (2) an eval set of 20-50 natural-language requests with expected end-state predicates (e.g. "a `study-timer` widget exists on page X with size >= 2x2"), run against the real model with 3 trials each (`pass^3`), in CI on prompt or model changes; (3) a forbidden-ops suite (requests that should NOT delete, should ask first, should refuse) graded by trajectory subset match; (4) a small model-judge rubric only for layout aesthetics.
- Guardrails at the applier, independent of the model: Zod validation of every op (ids exist, enums valid), an allowlist of mutable fields, a cap on ops per turn (e.g. 25) and on destructive ops per turn (e.g. 0 without confirmation), size bounds on notes/HTML, rate limits on custom-widget regeneration, and an inverse-op journal so any applied batch is undoable in one click. Rejected ops go back to the model as `is_error` tool results with the reason, which is the same "retry once" loop the GenUI literature recommends.
- For Approach C, add static checks before loading HTML (reject `<script src=`, `import(`, `fetch(`, `XMLHttpRequest`, `localStorage` by regex as a cheap first filter; the CSP is the real enforcement), a render smoke test in a hidden frame with a timeout, and a size cap.

### Gaps
- No source specifically documents snapshot testing of LLM action sequences for UI apps; the plan above is synthesised from the agent-eval literature.
- No measured failure rates for current Claude 5.5 models on catalog-constrained UI generation were found; VGV references a separate benchmark post that was not fetched.
