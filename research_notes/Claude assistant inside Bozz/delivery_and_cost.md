# Delivering a Claude-powered assistant inside a small indie Tauri desktop app: where the key lives, who pays, cost and abuse control

Scope: Bozz (Tauri 2 + React desktop app, Supabase backend with Google OAuth, solo student founder, handful of users today, hoping for hundreds, "Plus" paid tier exists). Date of research: 2026-10-15. All prices USD. Primary sources are platform.claude.com / anthropic.com / supabase.com / cloudflare docs fetched live on 2026-10-15; secondary sources are flagged.

## Key question 1: Option 1, bring-your-own-key (BYOK). Is direct client-side access allowed, what about Tauri native fetch, how do other apps do BYOK UX, how hard is it for a consumer to get a key, and can Claude subscription / Claude Code OAuth tokens be used?

### Takeaway
BYOK with direct client calls is explicitly supported by Anthropic (CORS enabled since Aug 2024 via the `anthropic-dangerous-direct-browser-access: true` header) and the Claude Code legal page explicitly permits users configuring their own API key as long as usage is billed to the key owner. What is explicitly forbidden (Feb 2026 docs update, enforced since Jan 2026) is routing through Claude Free/Pro/Max subscription credentials or collecting Claude.ai OAuth/session tokens in a third-party app. The friction is real: a consumer needs a separate Console account with prepaid credits (third-party guides say $5 minimum), and no published data exists on what share of consumer users will actually do this.

### Cited Findings
- Anthropic enabled CORS on its JSON API in Aug 2024; browser requests must include `anthropic-dangerous-direct-browser-access: true` alongside `x-api-key`, `anthropic-version` and `content-type`. Simon Willison notes Anthropic was reluctant because an embedded key can be stolen by anyone with access to the site, and lists "bring your own API key" (each user supplies their own key to the client-side app) as a legitimate use. [Simon Willison, 2024-08-23](https://simonwillison.net/2024/Aug/23/anthropic-dangerous-direct-browser-access/)
- Without the header, browser requests fail with "401 CORS requests must set 'anthropic-dangerous-direct-browser-access' header" (GitHub issue reports). [page-assist issue #511](https://github.com/n4ze3m/page-assist/issues/511); [ChainForge issue #367](https://github.com/ianarawjo/ChainForge/issues/367)
- The official CORS doc page at `platform.claude.com/docs/en/api/cors` returned 404 on 2026-10-15, so I could not confirm the current official wording of the policy; the header is still referenced by current third-party projects. [fetch attempt, 404](https://platform.claude.com/docs/en/api/cors)
- Claude Code legal page (current): "Developers building products or services that interact with Claude's capabilities ... should use API key authentication through Claude Console ... Anthropic does not permit third-party developers to offer Claude.ai login into their own applications, or to route requests through Free, Pro, or Max plan credentials on behalf of their users. Moreover, developers may not collect, store, or intermediate Claude.ai credentials or session tokens." [code.claude.com legal-and-compliance](https://code.claude.com/docs/en/legal-and-compliance)
- Same page, the BYOK carve-out: "This does not restrict how customers provision and manage their own API keys ... for example, configuring an API key in a development environment, secrets manager, or machine image for use by the customer's own authorized users, provided the resulting usage is billed to the key owner under their agreement with Anthropic ... and is not resold or intermediated." [code.claude.com legal-and-compliance](https://code.claude.com/docs/en/legal-and-compliance)
- Same page: OAuth authentication "is intended exclusively for purchasers of Claude Free, Pro, Max, Team, and Enterprise subscription plans and is designed to support ordinary use of Claude Code and other native Anthropic applications." Anthropic "reserves the right to take measures to enforce these restrictions and may do so without prior notice." [code.claude.com legal-and-compliance](https://code.claude.com/docs/en/legal-and-compliance)
- Secondary coverage: enforcement began blocking Max OAuth access in third-party clients on 2026-01-09; a documentation update on 2026-02-19 clarified that consumer-plan OAuth tokens in third-party tools (including the Agent SDK) violate the consumer terms. [WinBuzzer 2026-02-19](https://winbuzzer.com/2026/02/19/anthropic-bans-claude-subscription-oauth-in-third-party-apps-xcxwbn/); [Gigazine 2026-02-20](https://gigazine.net/gsc_news/en/20260220-anthropic-third-party-block); [daveswift.com](https://daveswift.com/claude-oauth-update/)
- Usage Policy prohibits "reselling, proxying, or providing access to Claude through unauthorized means" and "routing requests through consumer subscriptions". [Anthropic Usage Policy](https://www.anthropic.com/legal/aup)
- Claude Code name/logo: you may say in plain text that your product runs Claude Code, but may not use the Claude Code or Anthropic names or logos in your own product, feature or company name, or in a way suggesting endorsement; other uses go through the Trademark Guidelines. [code.claude.com legal-and-compliance](https://code.claude.com/docs/en/legal-and-compliance)
- Console billing is prepaid credits bought before use; if you run out you cannot call the API. Auto-reload (threshold + target balance) exists. Purchased credits expire one year after purchase and are non-refundable. **Max and Team plans include monthly API credits** claimable by linking a Console org to the plan; these cannot be used in Claude Code or the Claude apps and expire each billing cycle. The article does not say Pro includes API credits. [support.claude.com: How do I pay for my API usage](https://support.claude.com/en/articles/8977456-how-do-i-pay-for-my-api-usage)
- Minimum initial top-up is reported as $5 USD by third-party guides (not confirmed on an official page). Key creation works without payment but requests fail until credits exist (third-party claim). [apisrouter.com guide](https://apisrouter.com/claude-api-key-guide); [aisuru docs](https://docs.aisuru.com/en/generative-ai/advanced/providers-api-keys/claude-console-managing-anthropic-api-keys)
- Third-party guides: "A Pro or Max chat subscription does not cover API access. The Console is billed separately." [lilys.ai guide](https://lilys.ai/en/notes/claude-code-20260115/anthropic-claude-api-key)
- Tauri 2 `tauri-plugin-http`: the JS `fetch` is a near drop-in for Web Fetch; requests are executed by backend commands (`fetch`, `fetch-send`, `fetch-read-body`, `fetch-cancel`) built on Rust `reqwest` (re-exported as `tauri_plugin_http::reqwest`); you must allow-list origins in `src-tauri/capabilities/default.json` under `http:default` (`allow` / `deny` URL patterns); forbidden headers are ignored unless the `unsafe-headers` feature is enabled. The doc page does not explicitly state CORS bypass or body streaming. [v2.tauri.app http-client plugin](https://v2.tauri.app/plugin/http-client/)
- BYOK UX examples:
  - Cursor: custom keys for OpenAI, Anthropic, Google, Azure, Bedrock; keys are not stored on Cursor's servers but every request still transits Cursor's backend (sent over encrypted connections, discarded after the request); own-key requests are billed by the provider and don't consume Cursor credits; Teams/Enterprise pay an extra Cursor Token Rate of $0.25 per million tokens; ZDR does not apply to own-key requests. [cursor.com docs: API keys](https://cursor.com/docs/settings/api-keys)
  - Raycast Pro: $8/mo ($96/yr), 500 AI credits/month included, dozens of hosted models (Claude Sonnet 4.6 included; Opus 5 needs the Advanced AI add-on); BYOK ("custom keys") supported for OpenAI, Anthropic and Google. [raycast.com/pro](https://www.raycast.com/pro)
  - Obsidian plugins historically stored keys in plaintext `data.json` (which syncs across devices via Obsidian Sync/iCloud); Obsidian added a `SecretStorage` API (Obsidian 1.11.4+) so plugins reference secrets by name; values do not sync between devices, so users re-enter per device. [Obsidian docs: secret storage](https://docs.obsidian.md/plugins/guides/secret-storage); [Obsidian forum](https://forum.obsidian.md/t/store-secrets-like-api-key-outside-of-data-json/56035); [gemini-helper 1.21.0 notes](https://newreleases.io/project/github/takeshy/obsidian-gemini-helper/release/1.21.0)
- No published adoption data for BYOK: a Google AI forum poster hypothesised that maybe "even 10%" of users would ignore a "don't share your API key" warning, explicitly framed as needing an experiment. [discuss.ai.google.dev](https://discuss.ai.google.dev/t/are-bring-your-own-api-key-apps-ok-under-google-geminis-tos/5127); [dev.to: Stop paying for your users' AI usage](https://dev.to/c9dn/stop-paying-for-your-users-ai-usage-5bl5)

### Inferences
- For Bozz the safest BYOK architecture is: Tauri native `fetch` from Rust (no CORS involvement at all, so the "dangerous" header is irrelevant), key stored in the OS keychain (e.g. `tauri-plugin-stronghold` or the `keyring` crate; not verified here), never in `dashboard.json` (which syncs to Supabase and would leak the key the same way Obsidian `data.json` did). Billing goes to the user's own Console org, which matches the "billed to the key owner" carve-out.
- Never accept a Claude.ai login, `claude setup-token` output or `ANTHROPIC_AUTH_TOKEN` from a subscription; this is the one explicitly banned pattern, and enforcement is server-side without notice.
- Expect BYOK conversion among non-developer students to be low single digits to low tens of percent (no data; the only number found is a "maybe 10%" guess). The Max-plan monthly API credits are a small tailwind: a Max subscriber already has claimable API credit without a card top-up.
- Show spend in-app by summing `usage` from each response (input, cache_creation, cache_read, output) times the published rates; the Usage & Cost Admin API is org-level and needs an admin key, so it is not usable to show an end user their spend from inside the app.

- Minimum credit top-up ($5) only from third-party guides.
- Did not verify how Zed, Continue, Jan, LM Studio, chatbox, TypingMind or Open WebUI store keys (search budget exhausted).

## Key question 2: Option 2, app-provided key behind a proxy (Supabase Edge Function vs Cloudflare Workers vs Vercel Edge), limits, streaming, quotas, abuse control, Anthropic-side spend isolation

### Takeaway
A Supabase Edge Function proxy fits Bozz's existing auth: Free tier gives 500K invocations/month, 150 s wall-clock, 2 s CPU, 256 MB, and streaming works via `ReadableStream` responses; Pro ($25/mo) raises wall-clock to 400 s and includes 2M invocations. Cloudflare Workers Free gives 100K req/day with no duration limit on HTTP streaming but only 10 ms CPU. Anthropic-side you can isolate the assistant into its own Workspace with its own spend and rate limits, set an org spend limit below the Start-tier $500/mo cap, and read spend via the Usage & Cost Admin API; per-user quotas must be your own Postgres rows under RLS.

### Cited Findings
- Supabase Edge Function limits: wall-clock 150 s (Free) / 400 s (paid); CPU time 2 s per request (async I/O not counted); memory 256 MB; request idle timeout 150 s (504 if no response); 100 functions per project on Free, 1000 on Pro; recursive calls capped at 30 per trace per 60 s. [supabase.com/docs/guides/functions/limits](https://supabase.com/docs/guides/functions/limits)
- Supabase pricing: Free $0 with 500,000 Edge Function invocations included, 500 MB DB, projects paused after one week of inactivity; Pro from $25/mo with 2,000,000 invocations included and $2 per additional million, 8 GB disk, never paused, spend cap on by default, $10/mo compute credits. [supabase.com/pricing](https://supabase.com/pricing)
- Streaming out of an Edge Function: the ElevenLabs/Supabase guide builds a `ReadableStream`, `tee()`s it, and returns `new Response(stream)`; the Supabase AI-inference blog returns a stream with `'Content-Type': 'text/event-stream'`; Supabase's examples repo has a "Server-Sent Events in Edge Functions" web-stream example. [ElevenLabs guide (Supabase streaming)](https://elevenlabs.io/docs/it/eleven-api/guides/how-to/text-to-speech/streaming-and-caching-with-supabase); [DEV: AI inference in Edge Functions](https://dev.to/supabase/ai-inference-now-available-in-supabase-edge-functions-3ae1); [Supabase Edge Functions docs](https://supabase.com/docs/guides/functions.md)
- Cloudflare Workers: Free 100,000 requests/day (reset midnight UTC, excess returns Error 1027), 10 ms CPU per request, 128 MB, 50 subrequests; Paid no request limit, CPU up to 5 min (default 30 s), 10,000 subrequests; HTTP request duration unlimited on both plans; streaming responses have no enforced body size and run while the client stays connected. [developers.cloudflare.com Workers limits](https://developers.cloudflare.com/workers/platform/limits/)
- Anthropic spend limits: Start tier $500/mo cap, Build $1,000, Scale $200,000; reaching the cap returns 429 with `error_code: enforced_spend_limit_reached` and no `retry-after`; you can set your own lower org spend limit on the Billing page (then requests return 400 `invalid_request_error`, "You have reached your specified API usage limits", or "...workspace API usage limits" for a workspace limit). [platform.claude.com rate limits](https://platform.claude.com/docs/en/api/rate-limits)
- Per-Workspace limits: "you can set custom spend and rate limits per Workspace"; cannot set limits on the default Workspace; workspace limits are per limiter type (RPM / ITPM / OTPM). [platform.claude.com rate limits](https://platform.claude.com/docs/en/api/rate-limits)
- Start-tier rate limits for Sonnet 5.5 and Haiku 5.5: 1,000 RPM, 2,000,000 input tokens/min, 400,000 output tokens/min (same for Opus 5.5); new orgs may start in an Evaluation tier with lower limits. Cache reads do not count toward ITPM. [platform.claude.com rate limits](https://platform.claude.com/docs/en/api/rate-limits)
- Usage & Cost Admin API: `/v1/organizations/usage_report/messages` (1m/1h/1d buckets; filter/group by api_key_id, workspace_id, model, service_tier) and `/v1/organizations/cost_report` (daily, USD cents, group by workspace/description). Requires an Admin API key (`sk-ant-admin01-...`) or non-workspace-scoped key; "The Admin API is unavailable for individual accounts" (set up an organization). Data appears within ~5 min; poll once/min. [platform.claude.com usage-cost-api](https://platform.claude.com/docs/en/manage-claude/usage-cost-api)
- Commercial Terms: "Customer is responsible for all activity under its account" (D.5); customers may "power products for their own customers and end users" (A.1); no explicit clause on sharing keys. [anthropic.com commercial terms](https://www.anthropic.com/legal/commercial-terms)

### Inferences
- Invocation budget arithmetic: 300 active users × 50 requests/mo × 3 model round-trips (tool loop) = 45,000 invocations/mo, under 10% of the Free 500K. Even 1,000 users × 150 × 3 = 450K stays under Free. Invocations are not the constraint; the $25 Pro fee would be paid for no-pause + 400 s wall-clock, not for volume.
- Wall-clock risk: a multi-step tool loop where the Edge Function holds the connection open for the whole agentic turn can approach 150 s on Free. Better design: the Edge Function does exactly one Messages API call per invocation (streaming SSE to the client), and the Tauri client runs the tool loop (executing tools locally against the app state and calling the function again). This keeps each invocation to one model turn (typically 5-30 s), keeps CPU under 2 s (streaming is I/O), and keeps tool execution client-side where the data lives.
- Cloudflare Workers Free 10 ms CPU is enough for a pure pass-through SSE proxy but you would have to verify Supabase JWTs in the Worker (JWKS fetch, cached) and write quotas to Supabase over HTTP; more moving parts than keeping it inside Supabase. Vercel Edge was not researched (gap).
- Abuse controls to implement in Postgres (all behind RLS, written only by the Edge Function using the service role): per-user daily and monthly token budget rows, a `max_tokens` cap per plan (e.g. 1,500 output), model routing by plan (Haiku/Sonnet default, Opus only for Plus or on explicit "think harder"), request-rate cap per user (e.g. 10/min), and hard refusal when the org-level spend limit 400/429 comes back. Put the assistant key in a dedicated Anthropic Workspace so its spend/rate limits and Usage API grouping are separate from any other key use.

### Gaps
- Vercel Edge limits/pricing not fetched.
- Could not find official Supabase doc text on SSE specifics (buffering, idle timeout interaction with long streams); behaviour inferred from examples.
- Whether a solo-founder Console account can create an "organization" (needed for Admin API/Workspaces) was not verified beyond the docs tip.

## Key question 3: Option 3, hybrid (free = BYOK, Plus = included quota via proxy); what comparable apps charge and include

### Takeaway
Hybrid is the mainstream pattern among tools that expose model choice (Raycast, Cursor): a flat subscription with a metered allowance plus optional BYOK that bypasses the allowance. Pure productivity apps mostly bundle AI into the paid tier (Notion Business, Motion) or credit-meter it (Notion custom agents $10 per 1,000 credits, Motion 1,000-10,000 AI credits per seat). Numbers for Todoist, Things, Structured, Amie, Akiflow, Craft, Bear, Superhuman were not verified from primary pages.

### Inferences
- For a student audience, a credit-metered Plus allowance (e.g. 150 assistant requests/mo on Sonnet 5.5, which costs the founder roughly $3-6 per heavy user per month per the model below) with BYOK as the escape hatch for power users mirrors Raycast's shape and keeps worst-case cost bounded.
- Advertise the allowance in requests or "credits", not tokens; every comparable consumer product hides token math.

## Key question 4: Cost model (Opus 5.5 / Sonnet 5.5 / Haiku 5.5 with prompt caching) and which tier is sensible for tool-calling "edit my app" requests

### Takeaway
With a 6-10K cached prefix and 500-1,500 output tokens, a blended request costs about $0.02 on Sonnet 5.5, $0.04 on Opus 5.5 and $0.001 on Haiku 5.5; at 50 requests/user/month that is roughly $1 / $2 / $0.05 per active user, so 300 active users on Sonnet is on the order of $280-460/mo plus Supabase. Anthropic's own migration guidance positions Sonnet 5.5 at `medium` effort as the default for agentic coding and multistep tool use (beats Sonnet 5 at `high` at under a fifth of the cost) and Haiku 5.5 for routing/extraction/sub-agent work; Opus 5.5 is the upgrade for the hardest long-horizon tasks.

### Cited Findings
- Official prices (per MTok): Opus 5.5 input $4, 5-min cache write $5, 1-h cache write $8, cache hit $0.20, output $20. Sonnet 5.5: $2 / $2.50 / $4 / $0.10 / $10. Haiku 5.5 (prompt up to 100K tokens): $0.10 / $0.125 / $0.20 / $0.01 / $0.50; (prompt over 100K): $0.50 / $0.625 / $1 / $0.05 / $2.50. Cache hits on Opus 5.5 and Sonnet 5.5 are 0.05x base input (not the usual 0.1x). Batch API is 50% off (Sonnet $1/$5, Haiku $0.05/$0.25, Opus $2/$10). 1M context at standard pricing except Haiku 5.5, which has the two rate cards by prompt length; each request priced on its own, counting cache reads toward the 100K threshold. [platform.claude.com pricing](https://platform.claude.com/docs/en/about-claude/pricing)
- Caching: minimum cacheable prefix is model-dependent (512-4096 tokens); 5-min TTL by default, 1-h optional; caching pays off after one read at 5-min TTL (1.25x write) or two reads at 1-h (2x write). [platform.claude.com pricing](https://platform.claude.com/docs/en/about-claude/pricing)
- Cache reads do not count toward ITPM rate limits, so caching the system prompt + tool schemas also multiplies effective throughput. [platform.claude.com rate limits](https://platform.claude.com/docs/en/api/rate-limits)
- Sonnet 5.5 guidance (Anthropic's `claude-api` skill bundled in Claude Code 2.1.295, `shared/model-migration.md`, section "Migrating to Claude Sonnet 5.5"): same prices as Sonnet 5; "Starting points: `medium` for agentic coding and multistep tool use; `low` for chat, content generation, classification, extraction"; "In Anthropic's testing it finishes agentic coding and multistep tool-use work in far fewer model requests than Claude Sonnet 5 ... On most agentic coding evals it scored higher at `medium` than Claude Sonnet 5 did at `high`, typically at under a fifth of the cost"; "for the hardest long-horizon work, an Opus model is the better choice". Thinking cannot be disabled on Sonnet 5.5 (`between_tools` mode is the thinking-off substitute at effort high or below); forced `tool_choice` `any`/`tool` returns 400 (use `auto` + `strict: true`). [Anthropic model migration guide (public counterpart of the bundled file)](https://platform.claude.com/docs/en/about-claude/models/migration-guide)
- Haiku 5.5 guidance (same source, "Migrating to Claude Haiku 5.5"): "for high-volume, latency-sensitive work such as classification, routing, extraction, and sub-agent tasks"; "substantially better at instruction following and at running as a sub-agent"; newer tokenizer produces ~30% more tokens than Haiku 4.5; effort default `medium`; no server-side refusal fallback; thinking on by default and billed as output. [same source](https://platform.claude.com/docs/en/about-claude/models/migration-guide)
- Opus 5.5 guidance (same source, "Migrating to Claude Opus 5.5"): at default `medium` effort it "matched or beat Claude Opus 5's `high`-effort results ... in fewer steps and with about half the tokens"; thinking cannot be disabled; effort default `medium`. [same source](https://platform.claude.com/docs/en/about-claude/models/migration-guide)
- Spend cap sanity check: Start tier cap $500/mo. [platform.claude.com rate limits](https://platform.claude.com/docs/en/api/rate-limits)

### Inferences (the arithmetic)
Assumptions: stable cached prefix (system prompt + tool schemas) = 6,000 tokens; per-request uncached input (app-state snapshot delta + user message + short history) = 2,000 tokens; output = 1,000 tokens (includes adaptive-thinking tokens at low/medium effort, which are billed as output even though hidden). Cache hit rate 70% (5-min TTL; students work in bursts), 30% of requests pay a 5-min cache write.

Per single-turn request (uses official prices above):

|---|---|---|---|
| Opus 5.5 | 6K x $0.20/M = $0.0012 + 2K x $4/M = $0.0080 + 1K x $20/M = $0.0200 = **$0.0292** | 6K x $5/M = $0.0300 + $0.0080 + $0.0200 = **$0.0580** | 0.7 x 0.0292 + 0.3 x 0.0580 = **$0.0378** |
| Sonnet 5.5 | 6K x $0.10/M = $0.0006 + 2K x $2/M = $0.0040 + 1K x $10/M = $0.0100 = **$0.0146** | 6K x $2.50/M = $0.0150 + $0.0040 + $0.0100 = **$0.0290** | **$0.0189** |
| Haiku 5.5 | 6K x $0.01/M = $0.00006 + 2K x $0.10/M = $0.0002 + 1K x $0.50/M = $0.0005 = **$0.00076** | 6K x $0.125/M = $0.00075 + $0.0002 + $0.0005 = **$0.00145** | **$0.00097** |

Fleet examples (Sonnet 5.5, 50 req/user/mo, mix 50% single-turn / 50% multi-step, about $0.030/request): 30 users about $46/mo; 100 users about $152/mo; 300 users about $457/mo (would hit the Start-tier $500 cap at roughly 330 users; request Build tier before then). On Haiku 5.5 the same 300 users cost about $24/mo. Add Supabase Pro $25/mo if the project must never pause.

- Rough rule: Opus is about 2x Sonnet, which is about 20x Haiku per request at this prompt shape, because output dominates and cache reads are nearly free on Opus/Sonnet 5.5 (0.05x).
- Sensible routing for Bozz: Haiku 5.5 for intent classification, quick captures and "what's on today" summaries (sub-cent); Sonnet 5.5 at effort `low`/`medium` with `strict: true` tools for the "edit my pages/tasks/habits" agent; Opus 5.5 reserved for Plus users on a "think harder" toggle or when a Sonnet attempt fails validation. Keep `max_tokens` capped per plan (e.g. 2,000) since thinking tokens count toward it and are billed.
- Prompt-cache hygiene matters: put the app-state snapshot after the cache breakpoint (it changes every request); keep tool schema order deterministic; a 1-h TTL on the system/tools prefix costs 2x write but survives student breaks between requests.

### Gaps

## Key question 5: Compliance (Usage Policy / Commercial Terms for end-user products, Supabase RLS for quota tables, GDPR angle for sending student notes to Anthropic, retention/ZDR)

### Takeaway
Anthropic requires consumer-facing chatbots/agents to disclose that the user is interacting with AI (the disclosure need not name Claude or Anthropic) and to tell users outputs may be inaccurate; no "Claude" in product names/logos without permission. Conversation content is not retained by default on the Messages API for Opus/Sonnet/Haiku 5.5 (the 30-day requirement applies only to Fable/Mythos "Covered Models"), API data is never used for training, and ZDR is a sales-negotiated per-organization arrangement; flagged content and legal holds are retained regardless. For GDPR the founder is the controller and Anthropic the processor under its DPA, and the app must get a clear opt-in before shipping a student's tasks/notes to the API.

- Usage Policy: consumer-facing chatbots and AI agents "must disclose to users that they are interacting with AI rather than a human"; "The disclosure does not need to identify Anthropic, Claude, or the model used"; may not "convince people they are interacting with a human"; products serving minors (under 18) must follow Anthropic's additional guidelines; agent builders are responsible for actions their agents take via tools. ### Inferences
- Minimum compliance checklist for Bozz: (1) a one-time "Bozz Assistant uses AI; answers can be wrong" notice at first use plus a persistent AI badge in the chat panel; (2) an explicit opt-in toggle before any page/task/note content is sent, with a plain-language note that content goes to Anthropic (US processor) under its DPA and is not used for training; (3) a "what gets sent" preview (the app-state snapshot) and a per-page "exclude from assistant" flag; (4) name it "Bozz Assistant" / "powered by Claude" in plain text only, no Claude logo; (5) since users may be under 18 (students), read Anthropic's minors guidelines before launch; (6) BYOK mode: state that the user's own Console terms and retention then apply.
- Quota tables: `assistant_usage(user_id, day, requests, input_tokens, output_tokens, usd_micros)` and `assistant_plan(user_id, plan, daily_cap, monthly_cap)`; RLS = users can `SELECT` only their own rows, no client `INSERT/UPDATE`; only the Edge Function (service role) writes, after the model response returns actual `usage`. Pre-check the cap before calling Anthropic, then decrement with the real numbers; this matches the earlier Bozz RLS lesson (topic_members was anon-readable).
- ZDR is not realistic for a solo student org (sales-negotiated), so the GDPR story rests on: processor DPA + no training + non-retention-by-default for the 5.5 models + user opt-in + data minimisation (send titles/snippets, not whole note bodies, unless the user asks).
