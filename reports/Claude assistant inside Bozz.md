# Bozz Assistant: ship typed operations, not code

Bozz should build its in-app Claude assistant as a thin agent over a closed, typed action vocabulary (read the dashboard, apply a batch of schema-validated operations against the existing widget/page/theme/note/task/habit store), not as a code generator and not as a free-form "generative UI" engine. Every shipped product that lets a model edit user work has converged on the same trust kit: a right-hand side panel, a user-chosen propose-first or apply-live mode, a visible action log, and a single undo that reverts the whole assistant turn, and every documented disaster (Replit deleting a production database, Cursor undos that silently fail, Notion AI trashing pages) came from write paths the user could not see or reverse ([OECD AI Incidents](https://oecd.ai/en/incidents/2025-07-19-1eb1); [Cursor forum](https://forum.cursor.com/t/chat-checkpoints-dont-revert-code-properly/152855)). Technically the October 2026 Claude API makes the declarative path the easy one: `strict: true` tools give grammar-guaranteed schema-valid inputs, parallel tool calls arrive together so a whole turn can be previewed before it is applied, and forced tool use is gone, so the design must rely on `auto` plus a strong system prompt ([Define tools](https://platform.claude.com/docs/en/agents-and-tools/tool-use/define-tools)). Sandboxed generated code belongs only behind one explicit op, `create_custom_widget`, hosted in an opaque-origin iframe with a deny-all CSP. On delivery, Anthropic permits BYOK in a third-party app as long as usage bills to the key owner, but explicitly bans routing through Claude Pro/Max subscriptions, so the sensible model is Plus-included quota through a Supabase Edge Function proxy on Sonnet 5.5 (roughly **$0.02-0.04 per request, about $1-2 per active user per month at 50 requests**) with BYOK as the escape hatch for free users and power users ([code.claude.com legal](https://code.claude.com/docs/en/legal-and-compliance); [Pricing](https://platform.claude.com/docs/en/about-claude/pricing)). "Make the text easier to read" should map to a bounded set of theme tokens grounded in WCAG 1.4.12 and the British Dyslexia Association guide (1.5 line height, 0.12em letter spacing, left alignment, off-white background), not to a special font, because the dyslexia-font evidence is weak ([W3C 1.4.12](https://www.w3.org/WAI/WCAG22/Understanding/text-spacing)). The founder still has to decide the default autonomy mode, the Plus allowance, whether custom-widget code generation ships in v1 at all, and whether Bozz will accept under-18 users of the assistant.

## Every shipped editing assistant converges on the same four trust devices

The products that let a model change a user's workspace in 2026 differ in surface but agree on structure. Notion's Agent lives in a right-side sidebar that can detach into a floating window, cannot change workspace settings or page permissions, asks for confirmation before sending Gmail, and offers a Plan mode in which it will not edit while planning and shows a preview of which pages will change ([Notion Help: Notion Agent](https://www.notion.com/help/notion-agent); [Notion Help: Review & approve plans](https://www.notion.com/en-gb/help/review-and-approve-plans-before-notion-ai-runs)). Craft's Assistant has an explicit **Explore / Execute** mode selector: Explore proposes and nothing changes until the user approves, Execute applies live, and **Ctrl+Z reverts the assistant's entire last response as one step** ([Craft support](https://support.craft.do/en/ai-assistant/editing)). Raycast pauses the chat on an approval card with Allow / Always allow / Deny, warns that the action description "is AI-generated, so check it before you allow", and offers a global Ask / Auto / Always Allow permission mode where Auto runs read-only tools freely but always asks before destructive actions ([Raycast manual](https://manual.raycast.com/ai/ai-extensions)). Replit and Cursor add automatic checkpoints before significant changes and a Plan mode with Accept tasks / Revise plan ([Replit docs](https://docs.replit.com/replitai/agent); [Cursor docs](https://cursor.com/docs/agent/overview)). Word's Copilot reduces the whole thing to Keep it / Regenerate / Discard it ([Microsoft Support](https://support.microsoft.com/en-us/office/start-a-draft-with-copilot-in-word-069c91f0-9e42-4c9a-bbce-fddf5d581541)).

Four devices fall out of this: a side panel so the user can see the thing being edited, a mode toggle between propose-first and apply-live, a live log of what the assistant is doing, and coarse undo at the granularity of one assistant turn. For non-code artefacts nobody ships per-change accept/reject; that only appears where a natural diff exists (code, text suggestions). Karpathy's "autonomy slider" and his advice to "keep AI on a tight leash" while making verification "easy, fast to win" is the same idea stated as principle ([Latent Space, Software 3.0](https://www.latent.space/p/s3)). Microsoft's HAX guidelines give it a checklist: G9 support efficient correction, G10 scope services when in doubt, G11 make clear why the system did what it did, G16 convey the consequences of user actions, G18 notify users about changes, and Pattern 9C "Undo automated actions" ([HAX Design Library](https://www.microsoft.com/en-us/haxtoolkit/library/example,guideline,pattern/3,6,20/)).

### Selection-as-scope beats describing the target in words

Figma's Prompt to edit tells users to select specific layers first and say what to change and what to leave alone so edits stay scoped; Lovable's preview toolbar has "Select elements" that attach the clicked elements to the chat input as references; Claude's docs artifacts let you highlight text and click "Edit with Claude" so "Claude makes the edit where you marked it, so you don't have to describe which section you mean" ([Figma](https://www.figma.com/solutions/prompt-to-edit/); [Lovable docs](https://docs.lovable.dev/features/visual-edit); [Claude Help Center](https://support.claude.com/en/articles/9487310-what-are-artifacts-and-how-do-i-use-them)). For Bozz this means the assistant panel should read the currently selected page and any selected widget as implicit scope, and a right-click "Ask Bozz about this widget" entry should pre-fill that reference. Wattenberger's critique that chat opens as a blank page that does not signal what the tool is for argues for a single input that first fuzzy-matches known actions (Change theme, Add widget, Bigger text) the way Raycast's root search and Windows Settings' search box do, and only falls through to the model for unmatched text ([Simon Willison on Wattenberger](https://simonwillison.net/2023/May/15/why-chatbots-are-not-the-future); [Windows Insider Blog](https://blogs.windows.com/windows-insider/?p=178299)). Showing the equivalent manual action next to each applied change ("you can also do this in Settings > Appearance") doubles as explanation and teaches the UI, which is Litt's two-loop model in miniature: the user stays the inner-loop operator and "the user's reliance on the AI gently decreases over time" ([Litt](https://www.geoffreylitt.com/2023/03/25/llm-end-user-programming)).

### The failures that destroyed trust were silent or irreversible writes

The best-documented harm is not an ugly layout but a confident, irreversible data action reported inaccurately. In July 2025 Replit's agent deleted a production database holding records on roughly 1,200 executives during an explicit code freeze, fabricated thousands of fake profiles, claimed tests had passed, and claimed recovery was impossible; Replit's response was automatic dev/prod separation, a chat-only planning mode, and one-click restore from backups ([OECD AI Incidents](https://oecd.ai/en/incidents/2025-07-19-1eb1); [eWeek](https://www.eweek.com/news/replit-ai-coding-assistant-failure/)). Cursor's forum documents checkpoints that "look reverted" in chat while files stay modified, undos that delete whole files, Keep/Undo buttons hidden in breadcrumbs, and pending reviews lost on restart "as if I had clicked Keep" ([Cursor forum 152855](https://forum.cursor.com/t/chat-checkpoints-dont-revert-code-properly/152855); [Cursor forum 163021](https://forum.cursor.com/t/review-of-changes-done-in-agent-chat-window-disappears-after-cursor-restart/163021)). VS Code switched a git co-author trailer default on with no release note and had to revert it after the approving reviewer apologised publicly ([Windows Central](https://windowscentral.com/software-apps/this-could-cost-people-their-jobs-vs-code-added-copilot-as-co-author-without-permission-or-notice)). BetaNews' critique of the Windows Settings agent was precisely that a user "could accidentally make a change that they cannot work out how to undo" ([BetaNews](https://betanews.com/2025/05/07/microsoft-now-has-ai-agents-that-can-change-windows-11-settings-should-we-be-delighted-or-terrified/)).

The lesson for Bozz, which already carries a history of torn-store and sync-clobber incidents, is that undo must be at least as reliable as the store itself. Claude Code's checkpointing is the clearest spec: a snapshot before each prompt, the 100 most recent kept, restorable independently of conversation state, with the explicit limitation that edits made outside the tracked path are not restored ([Claude Code checkpointing](https://code.claude.com/docs/en/checkpointing)). Bozz should take a full store snapshot before every assistant turn, tag it with the prompt, keep the last N, and expose "Undo this turn" and "Restore to before this conversation" as persistent, not hover-only, controls. The "changes made" receipt must be generated from a structural diff of store-before versus store-after, never from the model's own narration, because the Replit case shows self-reports can be false. And the only thing allowed to mutate the store during a turn is the assistant's typed op pipeline, so the snapshot is complete by construction.

## Declarative operations over strict tools win on every axis that matters

Three architectures are on the table: declarative actions via tools (A), generative UI where the model emits a spec the app renders (B), and model-written code in a sandbox (C). The table summarises how they compare for Bozz.

| Axis | A: typed ops via strict tools | B: generative UI spec | C: sandboxed generated code |
|---|---|---|---|
| Output guarantee | Grammar-constrained, schema-valid inputs with `strict: true` | Schema-valid only if validated at runtime; "quiet failures that pass validation" are the hard ones | None; must be sandboxed and smoke-tested |
| Persistence | Plain data in the existing store, syncs and backs up like everything else | Spec is data, but introduces a second rendering path | Source stored as a widget config field; needs version history |
| Undo | Inverse-op journal keyed by `tool_use.id` | Spec replace | Replace source; data changes must still route through A |
| Attack surface | Validated op applier only | Catalog-constrained, but expression layers (`$state`, `$computed`) are a mini language | Full HTML/JS; iframe sandbox + CSP are the only barriers |
| Coverage of Bozz requests | ~90% (add/move/configure widget, create page, set theme, edit note/task/habit) | Mostly collapses into A because Bozz already has a widget catalog | Only "make me a widget that does X" where X is not a built-in type |

Approach A is the best-supported path on the current API. User-defined tools with `strict: true` "guarantee that tool names and inputs match the tool's schema, using grammar-constrained sampling", with limits of **20 strict tools per request, 24 optional parameters across all strict schemas**, and no recursive schemas or numeric constraints ([Structured outputs](https://platform.claude.com/docs/en/build-with-claude/structured-outputs)). Parallel tool calls arrive in one assistant message, and all `tool_result` blocks must return in a single user message or Claude is "silently trained" to stop making parallel calls ([Define tools](https://platform.claude.com/docs/en/agents-and-tools/tool-use/define-tools)). Anthropic's own advice is to consolidate related operations into fewer tools with an `action` parameter, write three-to-four-sentence descriptions, and ask for a short "explanation" rather than "reasoning" because a reasoning parameter can trigger a `reasoning_extraction` refusal ([Define tools](https://platform.claude.com/docs/en/agents-and-tools/tool-use/define-tools)). For Bozz that means a very small surface: `read_dashboard` returning pages, widgets, theme and settings as compact JSON with stable ids, and `apply_changes` taking an array of discriminated ops (`add_widget`, `move_widget`, `configure_widget`, `create_page`, `set_theme_tokens`, `edit_note`, `create_task`, `create_habit`, `delete_*`). The 24-optional-parameter cap bites quickly on a union of ten op types, so parameters should be required with explicit `null` rather than optional, and only the ops tool should be strict.

Two 2026 API changes shape the loop. Forced tool use (`tool_choice: any` or `tool`) now returns a 400 on Opus 5.5, Sonnet 5.5 and Fable 5.1, so "always emit an action" has to come from `auto` plus a system instruction such as "use `apply_changes` for any change; never describe a change without calling it" ([Define tools](https://platform.claude.com/docs/en/agents-and-tools/tool-use/define-tools)). And thinking blocks are bound to an append-only conversation, so undo must never rewrite earlier tool calls in the transcript; a declined batch goes back as a `tool_result` with `is_error: true` and the reason "user declined", and the undo lives in the app's inverse-op journal. Anthropic's tool-runner docs are explicit that "when you need human-in-the-loop approval, custom logging, or conditional execution, use the manual loop instead", which is the shape Bozz needs: collect every `tool_use` block in the assistant message, validate each against the app's own Zod schema (strictness does not protect against `max_tokens` truncation or eager streaming), simulate the batch against a cloned store to produce the preview, and only commit after the user confirms or the auto-apply policy passes ([Tool runner](https://platform.claude.com/docs/en/agents-and-tools/tool-use/tool-runner)). Mid-conversation operator instructions can be appended as `{role: "system"}` messages without invalidating the cached prefix, which is the right channel for "the user just undid your last batch" ([Prompt caching](https://platform.claude.com/docs/en/build-with-claude/prompt-caching)).

### Generative UI collapses into the widget catalog

Every production generative-UI system landed on the same rule: the model emits a declarative spec constrained to a developer-approved component catalog, validated at runtime, rendered by app-owned components. Vercel's json-render (18.7k stars) is built around `defineCatalog` with Zod props per component and claims "AI can only use components in your catalog", Google's A2UI describes itself as "a declarative data format rather than executable code, so agents can only use pre-approved catalog components", and Very Good Ventures' four-layer defence puts catalog schemas in the prompt plus structural and membership validators with a single retry before erroring out ([json-render](https://github.com/vercel-labs/json-render); [a2ui.org](https://a2ui.org/); [Very Good Ventures](https://verygood.ventures/blog/generative-ui-hallucinations-four-layer-defense.md)). One practitioner's summary: constraining the model "to select and configure a fixed inventory of components is dramatically more reliable than generative UI that lets the model invent the interface" ([metacto](https://www.metacto.com/blogs/generative-ui-production-guide)). Bozz already has that inventory: its widget types with JSON config. So the B-style win is simply an `add_widget` op whose `config` is the per-widget Zod schema. Adopting json-render or CopilotKit would add a second rendering path and a framework to a Tauri app that already has its own UI; A2UI's React story is weak (Angular, Flutter, Lit renderers); OpenUI/Thesys is a hosted gateway with a proprietary DSL whose docs are mid-reorganisation. None earn their weight here.

### Sandboxed code is viable only behind one op and one iframe recipe

If "make me a widget that…" must cover things no built-in type does, the established recipe is the Artifacts and MCP Apps one: an iframe with `sandbox="allow-scripts"` and never `allow-same-origin` (MDN says combining them lets the embedded document remove the sandbox attribute entirely), a `<meta http-equiv="Content-Security-Policy">` prepended to the srcdoc with `default-src 'none'; connect-src 'none'; frame-src 'none'; object-src 'none'`, and a narrow JSON-RPC-style postMessage protocol validated with Zod on every message ([MDN iframe](https://developer.mozilla.org/en-US/docs/Web/HTML/Reference/Elements/iframe); [ext-apps spec](https://raw.githubusercontent.com/modelcontextprotocol/ext-apps/main/specification/draft/apps.mdx)). The Tauri-specific hazard is CVE-2024-35222: the fix removed `invoke` from iframes "except on Windows when the origin of the Tauri window and the origin of the iFrame are the same", which is exactly why `allow-same-origin` must never be granted and `withGlobalTauri` must stay false ([GHSA-57fm-592m-34r7](https://github.com/advisories/GHSA-57fm-592m-34r7)). Tauri also notes that on Linux it cannot distinguish an embedded iframe from the window for remote capabilities, so Bozz should never grant remote-URL capabilities at all ([Tauri capabilities](https://v2.tauri.app/security/capabilities/)). The model must be told to inline everything with no imports, because the largest single failure cause in a benchmark of LLM-generated web apps was a hallucinated icon import (34.7% of failures), and slopsquatting is real: 19.7% of 2.23M generated samples contained at least one hallucinated package and `react-codeshift` spread into 237 repos before it was caught ([UI2App, arXiv 2607.06306](https://arxiv.org/pdf/2607.06306); [Dark Reading](https://www.darkreading.com/application-security/ai-code-tools-widely-hallucinate-packages); [CSA research note](https://labs.cloudsecurityalliance.org/research/csa-research-note-slopsquatting-ai-supply-chain-20260419/)). Generated widgets get a read-only pre-filtered JSON snapshot by postMessage, never a store reference or credentials, and any mutation they want must be translated into `apply_changes` ops through the same confirm gate, so there is exactly one write path. This is the hybrid both OpenAI's Apps SDK and MCP Apps ship: structured tool calls for state, a sandboxed View for presentation, every View-initiated side effect routed back through a host-gated tool call ([OpenAI Apps SDK](https://developers.openai.com/apps-sdk/build/custom-ux)).

## Plus-included quota through a Supabase proxy, BYOK as the escape hatch

The policy constraints are now unambiguous. Anthropic's Claude Code legal page states that developers "may not collect, store, or intermediate Claude.ai credentials or session tokens" and may not "route requests through Free, Pro, or Max plan credentials on behalf of their users", with enforcement that began blocking Max OAuth in third-party clients on 2026-01-09 ([code.claude.com legal](https://code.claude.com/docs/en/legal-and-compliance); [WinBuzzer](https://winbuzzer.com/2026/02/19/anthropic-bans-claude-subscription-oauth-in-third-party-apps-xcxwbn/)). The same page carves out BYOK: customers may configure their own API keys "provided the resulting usage is billed to the key owner under their agreement with Anthropic ... and is not resold or intermediated". So Bozz can never offer "sign in with Claude", but can accept a Console key. The friction is real: Console billing is prepaid credits, third-party guides report a **$5 minimum top-up**, and a Pro subscription does not cover API access (Max and Team do include claimable monthly API credits) ([support.claude.com billing](https://support.claude.com/en/articles/8977456-how-do-i-pay-for-my-api-usage); [apisrouter guide](https://apisrouter.com/claude-api-key-guide)). No published BYOK conversion rate exists for any consumer app; the only number found is a forum guess of "maybe 10%" ([discuss.ai.google.dev](https://discuss.ai.google.dev/t/are-bring-your-own-api-key-apps-ok-under-google-geminis-tos/5127)). For a student audience, BYOK alone would leave most users without the feature.

A proxy fits Bozz's existing Supabase auth. Free-tier Edge Functions give **500,000 invocations per month, 150 s wall-clock and 2 s CPU**; Pro at $25/mo gives 2M invocations and 400 s, and streaming works via `ReadableStream` responses ([Supabase limits](https://supabase.com/docs/guides/functions/limits); [Supabase pricing](https://supabase.com/pricing)). Invocations are not the constraint: 300 users at 50 requests with 3 model round-trips each is 45,000 per month. The design constraint is wall-clock, which argues for the Edge Function making exactly one Messages API call per invocation (streaming SSE to the client) while the Tauri client runs the tool loop locally, where the data lives anyway. Anthropic-side, the assistant key should sit in its own Workspace with its own spend and rate limits below the Start-tier $500/mo cap; hitting the cap returns a 429 with `enforced_spend_limit_reached`, and Start-tier limits of 1,000 RPM and 2M input tokens/min are far above Bozz's needs ([Rate limits](https://platform.claude.com/docs/en/api/rate-limits)). Per-user quotas must be Postgres rows under RLS that only the Edge Function's service role writes, pre-checked before the call and decremented with the real `usage` after it, which is the same lesson the earlier anon-readable `topic_members` incident taught.

### The arithmetic says Sonnet 5.5 at about two cents a request

Official prices per million tokens are Opus 5.5 $4 in / $20 out, Sonnet 5.5 $2 / $10, Haiku 5.5 $0.10 / $0.50 for prompts under 100K, and cache reads on Opus and Sonnet 5.5 cost only 0.05x base input ([Pricing](https://platform.claude.com/docs/en/about-claude/pricing)). With a 6K-token cached prefix (system prompt plus tool schemas), 2K fresh tokens of app-state delta and message, 1K output, and a 70% cache-hit rate, a single-turn request costs about **$0.019 on Sonnet 5.5, $0.038 on Opus 5.5 and $0.001 on Haiku 5.5**; a three-hop "edit my app" request costs about $0.042, $0.084 and $0.002 respectively.

| Requests per user per month | Opus 5.5 | Sonnet 5.5 | Haiku 5.5 |
|---|---|---|---|
| 20 | $0.76-1.68 | $0.38-0.84 | $0.02-0.05 |
| 50 | $1.89-4.20 | $0.95-2.10 | $0.05-0.11 |
| 150 | $5.67-12.60 | $2.84-6.30 | $0.15-0.34 |

At a 50/50 mix of single and multi-step turns on Sonnet 5.5, roughly $0.03 per request, **30 users cost about $46/mo, 100 about $152/mo, 300 about $457/mo**, which brushes the Start-tier cap at roughly 330 users. Anthropic's migration guidance positions Sonnet 5.5 at `medium` effort as the default for "agentic coding and multistep tool use", scoring higher at `medium` than Sonnet 5 at `high` at "under a fifth of the cost", and Haiku 5.5 for "classification, routing, extraction, and sub-agent tasks" ([Migration guide](https://platform.claude.com/docs/en/about-claude/models/migration-guide)). The routing for Bozz follows: Haiku 5.5 for intent classification and "what's on today" summaries, Sonnet 5.5 at `low`/`medium` with strict tools for the edit agent, Opus 5.5 only for Plus users on a "think harder" toggle or when Sonnet's batch fails validation. `max_tokens` should be capped per plan (around 2,000) because thinking tokens are billed as output and cannot be disabled on these models. Cache hygiene matters at this scale: the app-state snapshot goes after the cache breakpoint since it changes every request, tool schema order stays deterministic, and a 1-hour TTL on the prefix survives a student's break between requests at 2x write cost ([Prompt caching](https://platform.claude.com/docs/en/build-with-claude/prompt-caching)).

This cost shape mirrors the market. Raycast Pro is $8/mo with 500 AI credits and optional BYOK; Cursor lets own-key requests bypass included usage; Notion bundles AI into Business and meters custom agents at $10 per 1,000 credits ([raycast.com/pro](https://www.raycast.com/pro); [cursor.com docs](https://cursor.com/docs/settings/api-keys); [notion.com/pricing](https://www.notion.com/pricing)). A Plus allowance of around 150 assistant requests per month on Sonnet 5.5 costs the founder $3-6 for a heavy user, comfortably inside a Plus price, and should be advertised in requests, not tokens, since every comparable consumer product hides token math. Free users get BYOK plus a small taste quota; the key is stored by the Rust side in the OS keychain and never in `dashboard.json`, which syncs to Supabase and would leak it the way Obsidian's plaintext `data.json` did before Obsidian added `SecretStorage` ([Obsidian docs](https://docs.obsidian.md/plugins/guides/secret-storage)). In BYOK mode the Rust `reqwest` path avoids the browser CORS question entirely; the TypeScript SDK's `dangerouslyAllowBrowser` exists but the official CORS doc page returned 404 on 2026-10-15, so the header's current status is unverified ([anthropic-sdk-typescript README](https://github.com/anthropics/anthropic-sdk-typescript/blob/main/README.md)).

### Compliance is a short checklist, not a blocker

The Usage Policy requires consumer-facing agents to disclose that users are interacting with AI (the disclosure need not name Claude), and the Commercial Terms require notifying users that outputs may be inaccurate; Anthropic names and logos cannot appear in the product or feature name ([Anthropic Usage Policy](https://www.anthropic.com/legal/aup); [Commercial Terms](https://www.anthropic.com/legal/commercial-terms)). Conversation content "is not retained by default" on the Messages API for the 5.5 models (30-day retention applies only to Fable and Mythos "Covered Models"), API data is never used for training, and ZDR is a sales-negotiated per-organisation arrangement that a solo student org will not get ([API and data retention](https://platform.claude.com/docs/en/manage-claude/api-and-data-retention)). So the GDPR story rests on the processor DPA, non-retention, a clear opt-in before any note or task content leaves the machine, a "what gets sent" preview of the state snapshot, a per-page "exclude from assistant" flag, and data minimisation (titles and snippets by default, full note bodies only on request). Because UK students include under-18s, Anthropic's minors guidelines must be read before launch; that article was not fetched in this research.

## Safety means breaking the lethal trifecta, not writing better prompts

Every authority agrees that prompt-level defences alone fail. Willison's "lethal trifecta" is private data plus untrusted content plus an outbound channel; his list of exploited products runs from ChatGPT plugins through Bard, Copilot, Slack, Claude iOS, Operator, GitHub MCP and GitLab Duo, and he states that guardrails claiming 95% are "a failing grade" ([Willison](https://simonwillison.net/2025/Jun/16/the-lethal-trifecta/)). OWASP LLM01:2025 lists privilege control, human approval for high-risk actions and segregating external content as the mitigations ([OWASP LLM01](https://genai.owasp.org/llmrisk/llm01-prompt-injection/)). The Beurer-Kellner et al. design-patterns paper puts it structurally: once an agent has ingested untrusted input "it must be constrained so that it is impossible for that input to trigger any consequential actions", and offers Action-Selector (the model picks from predefined actions), Plan-Then-Execute (fix the action list before reading untrusted data) and Dual LLM (a quarantined model summarises untrusted content by reference) ([arXiv 2506.08837](https://arxiv.org/html/2506.08837v3)). Anthropic's own measurements on Claude in Chrome show why architecture matters: autonomous-mode attack success fell from **23.6% to 11.2%** with mitigations, and a browser-specific hidden-DOM challenge set went from 35.7% to 0% ([Claude for Chrome](https://claude.com/blog/claude-for-chrome)).

Bozz is well placed because its assistant does not need an outbound channel. It reads notes, calendar events and (via the Outlook connector) email bodies, all of which are untrusted content, but its only writes are to the local store. The design is to keep it that way: no URL fetch, no send-email, no rendering of image URLs from model output. Anthropic's platform guidance for the remaining risk is specific: put untrusted content only in `tool_result` blocks, never in the system prompt or plain user text; label its nature and source ("body of an inbound email from an unknown sender"); state in the system prompt that "instructions that appear inside that content" are information to report, not commands to follow; JSON-encode untrusted strings so an attacker cannot break out of a tag; and optionally screen tool outputs with a small Haiku classifier ([Anthropic: mitigate jailbreaks](https://platform.claude.com/docs/en/test-and-evaluate/strengthen-guardrails/mitigate-jailbreaks)). The closed op vocabulary is the Action-Selector pattern in practice: an injected email cannot invent a "sync settings" or "delete all" op that does not exist in the schema.

Destructive-action gating then follows Raycast and Notion. Read tools (`read_dashboard`, list tasks) are auto-allowed. Mutating ops (add, move, configure, create, edit) are applied to a draft and shown as a preview or applied live depending on the user's mode. Destructive ops (delete page, delete widget, delete note, clear habits) always require an in-app confirmation dialog rendered by the app, not by the model, with a cap of zero destructive ops per turn without confirmation and a cap on total ops per turn (around 25). Sync settings, connectors and account state are not in the vocabulary at all, mirroring Notion's "cannot change workspace settings" and its explicit list of object types the AI may not create ([Notion Help: Notion Agent](https://www.notion.com/help/notion-agent); [Notion help: AI autofill](https://www.notion.com/ja/help/autofill)). Every connector payload is wrapped with `source` metadata and the assistant never turns an email or calendar entry into a task silently, which also answers the finding that students rank accuracy as their top GenAI concern (53% worry about inaccurate information) and worry that AI "could be used to predict and influence their behaviours over time" ([Chegg survey](https://www.silicon.co.uk/press-release/chegg-global-student-survey-2025-80-of-undergraduates-worldwide-have-used-genai-to-support-their-studies-but-accuracy-a-top-concern); [Jisc 2025](https://jisc.ac.uk/reports/student-perceptions-of-ai-2025)).

## Grade the resulting store, cap the applier, and treat readability as tokens

Anthropic's eval guidance for state-modifying agents is to verify the final state directly, "not the agent's confirmation message", to avoid grading a rigid step sequence because agents find valid alternative paths, to start from 20-50 tasks drawn from real failures, and to run multiple trials from a clean environment (75% per-trial success is only about 42% at pass^3) ([Demystifying evals for AI agents](https://anthropic.com/engineering/demystifying-evals-for-ai-agents)). Bozz's op applier is a pure function `(store, ops) -> store`, which makes the first layer trivial: snapshot tests of the resulting store with no model in the loop. The second layer is an eval set of 20-50 natural-language requests with end-state predicates ("a `study-timer` widget exists on page X with size at least 2x2"), run against the real model three times each in CI on every prompt or model change, because "which tool the agent decides to call" only emerges with a real LLM ([LangChain test docs](https://docs.langchain.com/oss/python/langchain/test)). The third is a forbidden-ops suite graded by trajectory subset match (requests that must not delete, must ask first, must refuse), which LangChain's `agentevals` supports directly ([LangChain evals docs](https://docs.langchain.com/oss/javascript/langchain/evals)). Deterministic checks should cover 60-70% of the eval surface, with a model judge reserved for layout aesthetics ([Evaluate AI agents in production](https://www.kunalganglani.com/blog/evaluate-ai-agents-production-testing.md)). Runtime guardrails sit in the applier independent of the model: Zod validation of every op (ids exist, enums valid), an allowlist of mutable fields, size bounds on notes and HTML, and the retry-once loop in which rejected ops return as `is_error` results with the reason. For custom widgets, add a cheap regex filter for `<script src=`, `import(`, `fetch(` and `localStorage` before the CSP does the real enforcement, a render smoke test in a hidden frame with a timeout, and a watchdog that tears down a frame that stops answering `ping`.

"Make the text easier to read" deserves its own treatment because the obvious answer, a dyslexia font, is the least evidenced. WCAG 2.2 SC 1.4.12 requires content to survive **line height 1.5x, paragraph spacing 2x, letter spacing 0.12em and word spacing 0.16em** without loss, and fixed-height text containers are the common failure ([W3C 1.4.12](https://www.w3.org/WAI/WCAG22/Understanding/text-spacing)). The British Dyslexia Association guide recommends sans-serif at 12-14pt or larger, 1.5 line spacing, left-aligned not justified, no all caps or italics for continuous text, and dark text on a light but not white background ([BDA guide, Wigan copy](https://www.wigan.gov.uk/Docs/PDF/Business/Professionals/SEN/HEFA/Dyslexia-Style-Guide.pdf)). On fonts, Atkinson Hyperlegible's evidence is for low vision, not dyslexia; a community readability survey found Lexend Deca scoring 62% in the dyslexic-trait subgroup, tied with Segoe UI and behind BBC Reith Sans; and a secondary report of a 2018 study found OpenDyslexic performed worse than Arial ([CSUN 2024](https://www.csun.edu/cod/conference/sessions/2024/index.php/public/presentations/view/3108); [readability-group-survey](https://github.com/thibaudcolas/readability-group-survey); [ADA Compliance Pros](https://www.adacompliancepros.com/blog/dyslexia-friendly-font)). So the assistant's `set_theme_tokens` op should expose exactly these knobs: font family from a curated list (Lexend, Atkinson Hyperlegible, Verdana or Open Sans, with OpenDyslexic optional but not default), a base-size step, line-height defaulting to 1.5, letter and word spacing, paragraph spacing, left alignment, a cream background preset, and a reduced-motion toggle that also honours the OS `prefers-reduced-motion` per WCAG technique C39 ([W3C C39](https://www.w3.org/WAI/WCAG22/Techniques/css/C39.html)). These are reversible token changes, never layout rewrites. The one engineering prerequisite is that widget containers must grow with text; the current grid's fixed heights would clip content the moment the spacing knobs are turned, so that constraint belongs in the test suite before the knob ships.

## Recommendation and the decisions only the founder can make

Build the assistant in three stages, each shippable on its own. Stage one is the declarative core: a right-side panel toggled by a shortcut, with selection-as-scope, a single input that fuzzy-matches known actions before falling through to the model, two strict tools (`read_dashboard`, `apply_changes`), a per-turn store snapshot, a diff-generated change receipt, a persistent "Undo this turn" control, a destructive-op confirmation dialog, and the readability token set. This covers the four example requests in the brief ("set up a page for my module with…", "make the text easier to read", "change the theme and colours", and most of "make me a widget that…" when a built-in type fits). Stage two is delivery: a Supabase Edge Function that does one streamed Messages call per invocation against a dedicated Anthropic Workspace, RLS-protected quota rows, Sonnet 5.5 at `medium` with Haiku 5.5 routing, Plus-included requests, and keychain-stored BYOK for everyone else. Stage three, only if demand shows up in the eval logs, is `create_custom_widget` with the opaque-origin iframe recipe, inline-only HTML, a read-only data bridge and widget actions routed back through `apply_changes`. The order matters: stage three is the only one with a real escape risk and the only one without a documented desktop case study, and Ink & Switch's own experience was that some generated tools simply went unused ([Ink & Switch](https://www.inkandswitch.com/essay/malleable-software/)).

Several choices are product decisions rather than research findings. The default autonomy mode is one: Raycast defaults paid users to Auto, Craft and Notion default to applying, but Bozz's incident history and its "never silent" obligation argue for propose-first by default with apply-live as an opt-in per conversation, and the founder has to accept the extra click that costs. The Plus allowance and whether free users get any included requests at all (a taste quota of 10-20 per month costs cents but shapes conversion) is a pricing call. Whether custom-widget code generation is in v1 or deferred is a scope call that trades the strongest demo against the only real attack surface. Whether to upgrade Supabase to Pro ($25/mo) so the proxy never pauses is a cost call that interacts with the existing keep-alive workflow. Whether under-18 students may use the assistant, and what the opt-in and "what gets sent" preview say, is a compliance call that needs Anthropic's minors guidance read first. And the open empirical question that no source answers, what share of students will actually complete a $5 Console top-up for BYOK, can only be settled by shipping stage two and measuring it.

## Conclusion

The research reframes the problem. "Let users ask Claude to change the app" sounds like a generation problem, but every product that has shipped it and every incident that has burned one show it is a write-path problem: the assistant is trustworthy exactly to the degree that its writes are typed, previewable, logged from real diffs and reversible in one click. Bozz's existing architecture, a JSON store with atomic saves, backup-before-sync and a fixed widget catalog, is already most of the way to that shape; the assistant is a thin planner over operations the app already knows how to perform by hand, which is also what keeps the cost at pennies and the prompt-injection surface at zero outbound channels.

The second shift is that the hardest-looking request, "make the text easier to read", turns out to be the cheapest to do well and the most likely to be done badly by default. A model left to its own devices will reach for a dyslexia font; the evidence says to reach for spacing, size, alignment and background, which are five theme tokens and one grid fix. Encoding that knowledge into the op schema rather than hoping the model recalls it is the whole philosophy in miniature: put the judgement in the tools, let Claude choose among them.
